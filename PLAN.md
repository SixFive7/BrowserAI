# BrowserAI — implementation plan

What to build, and what is known to go wrong while building it.

This plan is **consumed as the code is written**. Every section is a requirement
waiting to become a file in this repository; when it has, the section has done its
job. That is what separates it from [`README.md`](README.md), which carries the
architecture, the scope boundary and the reasoning behind each decision and stays
true for as long as the decision does — and from [`kb/`](kb/README.md), which
carries the measurements and goes stale when upstream ships rather than when we
change our minds.

Work settled in intent but not yet done is tracked in [`TODO.md`](TODO.md).

---

## How this plan ends

**The plan is consumed and then deleted.** Each section below is one file. As the
code that satisfies a section lands, the section is marked `built` and records
what implements it. When every section is `built`, the whole plan is audited once
with extreme scrutiny for anything missed — and if it is complete, it is deleted.

That is why it is a folder rather than a document. A section that is its own file
is marked done and removed on its own, so the ending is a folder that empties as
the build proceeds rather than one irreversible final act. It is also why the
`Implemented by` column exists: without it, the final audit means re-reading
everything cold and hoping.

### What was decided, and what is raised

**Decided: the notices were incomplete and now ship.** `ModelContextProtocol`
and `ModelContextProtocol.Core` are Apache-2.0 and seventeen
`Microsoft.Extensions.*` assemblies are MIT; all nineteen are compiled into
`BrowserAI.exe` exactly as Velopack is, and a NuGet package's licence never
leaves the machine's package cache. §4(a) is stricter than MIT's notice clause,
not looser, and the product is publicly distributed. [Item 13](PRE-RELEASE.md#13-third-party-notices-ship)
now names **six** obligations with a `Corrected` note carrying its previous
text. **Two things measurement contradicted while closing it:** upstream's MCP
`LICENSE` grants **three** licences rather than one — Apache-2.0, MIT for
contributions never relicensed, CC-BY-4.0 for documentation — and its Apache
half **omits the appendix its own §4 points at**, which is reproduced unaltered
rather than completed. The `Microsoft.Extensions.*` list is derived from
`packages.lock.json` by `ThirdPartyNoticeTests`, so a package entering the
closure on a later bump is a red build rather than a licence nobody noticed.

**Decided 2026-08-17, and done: [pre-release](PRE-RELEASE.md) survives, and it
has moved.** It is the only release gate that exists — [there is no CI, no
scheduled job and no hook](README.md) — four of its fourteen items exist nowhere
else in executable form, three build scripts name it by filename and one writes
`"PRE-RELEASE.md item 11"` into every `manifest.json` shipped beside a `.nupkg`.
A file with those properties cannot sit in a folder whose defining property is
that it gets deleted.

**Why it moved now rather than on the day the plan goes.** The blocker the audit
named was real — it carried 18 outbound links into files that would be deleted,
ten into [testing](plan/testing.md), and its own rule is *"this file points; it
does not restate"* — and the answer was to **move** testing's release gate into
it rather than restate it. That is the one direction that produces no second
copy: `plan/testing.md` keeps the heading and points at
[`PRE-RELEASE.md#the-release-gate`](PRE-RELEASE.md#the-release-gate), so every
link that existed still resolves, and when testing is finally deleted the
sequence is already where it belongs. Doing it on deletion day instead would
have meant editing the only release gate this project has under time pressure,
in the same pass as twelve file removals.

### Why nothing was deleted, including the one complete section

[§F](plan/F-artifacts.md) is complete and was still left on disk. The rule this
document states is that a finished section is *"marked done and removed on its
own, so the ending is a folder that empties as the build proceeds"* — and that
is the point: **the build is not done.** No section was ever removed during the
build, so all thirteen files are still one interlinked document. §F alone is
cited by six sibling sections that remain live, by five rows of the surviving
[hazard index](plan/hazards.md), and by fourteen references from `src/`,
`tests/`, `build/` and [`README.md`](README.md). Removing it would convert
twenty-eight live citations into dead links or into weaker ones, for a folder
that keeps twelve files either way, and **a broken link is a worse outcome than
a section left on disk.**

The mechanical obstacle the audit named is **discharged as of 2026-08-17**, and
it was the larger of the two halves. [`plan/hazards.md`](plan/hazards.md) — the
one file that is *not* consumed — carried links into files that are, including
its own *Section shorthands* legend, the single line that gave every `§X` token
below it its meaning. **Re-counted by a third method** (every markdown inline
link whose target names one of the twelve consumed files, counted per
occurrence): **146 links on 109 lines, 107 of them table rows**, against the
audit's 135/106/104-of-139 and the recount's 136/107/105-of-135. The three
figures are not comparable and are all left as measured — the file has gained
rows since both earlier counts, including two on the day of the third. Every one
of those links is now the text it was linking with, the legend defines all ten
shorthands in words, and what remains points only at `kb/`, `README.md`,
`PLAN.md` and the code. **The hazard index can now outlive the plan**; the link
sweep reads 34 markdown files, 0 broken links, relative paths and `#anchor`
