# Hazard index

Every failure mode surfaced during research, in one checkable list. The overwhelming majority are **silent** — that is why they are enumerated rather than left to prose.

> **This is the one section of the plan that is not consumed.** Every other section is a requirement waiting to become a file, and is deleted once it has ([how this plan ends](../PLAN.md#how-this-plan-ends)). This one **outlives the build**: a hazard does not stop existing because the code that handles it was written. Rows gain a `Status` and the evidence that closed them; they are never deleted. When the rest of `plan/` is an empty folder, this file is what remains, and it is what a review of the finished product is checked against.

**This table is a lens, not a record.** Each row states the hazard in one line and points at the place that establishes it: an article under [`kb/`](../kb/README.md) where a measurement stands behind it, a section of this plan or of the [README](../README.md) where a decision does. Reading a row is not reading the evidence. A row whose *Established in* cell opens with `—` has no article to go to — it is a design consequence or a reading of the spec, recorded here only.

**If you find a new hazard, add it here** — and put the fact behind it in the `kb/` article that owns the topic. This list is what a reviewer checks the implementation against.

**It is maintained by addition, and it has been wrong by omission.** On 2026-08-15 eight silent-failure hazards established elsewhere in this document — the UNC-title stall, silent walk truncation, the forgeable window signal, strangers' paths from enumeration, races R3 and R5, Firefox's blocking modal, and disk exhaustion mid-provision — were absent from it. A gap here is a defect in the list, never evidence that the hazard is not real.

## The four columns, and what each is for

**Restructured 2026-08-16**, because a list that could only ever grow was answering half the question. It said what could go wrong and had no way to say *this one cannot happen any more, and here is why* — so a hazard that had genuinely been closed sat beside one nobody had touched, indistinguishable.

| Column | What it holds | The rule |
|---|---|---|
| **Why it happens** | The mechanism underneath the symptom, where it is knowable | **Never guessed.** `—` means the cause is not established, and an honest gap is worth more than a plausible story. This is the column that stops the same *class* recurring somewhere new: a fix aimed at a symptom closes one row, a fix aimed at a cause closes the ones nobody has written yet |
| **Established in** | Where the hazard is shown to be real | Unchanged |
| **Status** | `open` or `closed`, with the date it closed | Default `open`. A row is never deleted, so `closed` is the only way a hazard leaves the working set |
| **How we proved it** | The evidence that closed it | **A row marked `closed` with `—` here is not closed.** That is the whole point of splitting the two columns: `closed` is a claim, and this column is what makes it checkable |

**What `closed` may rest on, in order of strength.** A **measurement** that shows the failure cannot occur; a **test** that goes red if it starts occurring again; a **decision** that removes the possibility, such as not shipping the component the hazard lives in. Only the second of those keeps working without anyone watching, so a row closed by measurement or by decision names what would re-open it.

> ⚠️ **Corrected 2026-08-16 (previously "Nothing is closed by a passing test yet, because there is no suite yet. Every `closed` row below rests on a re-measurement or on a decision, and each says which.").** There is a suite, and [build-order step 5](build-order.md#5-the-two-custom-transports) closed the first nine rows with it — the `cmd.exe` argument failures, `StreamServerTransport`'s re-escaping, four environment hazards, and the `ExitCode` / `WaitForExit(int)` / `ArgumentList` trio. Each names the test that goes red if the hazard returns.

**A closure held by a decision or a measurement alone is one refactor from being wrong**, and the row is where that gets noticed — so a row closed without a test still names what would re-open it. Two of the nine say so explicitly rather than claiming more than they have: `WaitForExit(int)` is closed **by construction** with no analyzer banning the timed overload, and the `ExitCode` row closes only the half this build reaches, leaving `GetProcessById` untested and said so.

**Build-order step 6 closed six more and added one.** Five of the six are held by
tests that read the configuration **back from the kernel** rather than asserting
that the right call was made — limit flags, UI restrictions, handle inheritance —
which is the difference between proving a value and proving an intention. The
sixth, the *named job object* row, is closed **by construction with no test at
all** and says so, because an unnamed object has no name to fail to open. The row
that was added is a hazard in the checking rather than in the product, and it was
found by a failing assertion: a breakaway that *succeeds* is not a breakaway that
escaped.

**Build-order step 9 closed four, and three of them are closed by
*unreachability* rather than by handling.** The `ListToolsAsync` drop, the
`ContentBlock` drop and the typed `ListToolsResult` drop are all closed because
the product no longer constructs any of the types that lose data — the answer to
a `tools/list` or a `tools/call` is the child's own bytes, spliced by token
offset. That is the strongest form of closure available and it has a cost worth
naming: **nothing in the suite now checks whether the SDK still behaves that
way**, so the deviations' justification is a manual re-verification row rather
than a test, and the rows say so. The fourth, cancellation, is closed by a
mechanism that is **not the one its own remedy prescribed** — `ct.Register` fails
for the exact reason the hazard's description gives for the SDK failing.

**Build-order step 10 closed four, and one of them was closed by deleting the
mechanism the row was written around.** The *"a lock held by a dead instance"*
row was recorded against the current launcher's signature heuristic; the
replacement has no heuristic at all, because the OS releases the handle when the
holder dies and `(pid, creationFileTime)` decides whether the record left behind
names the process that is still there. The mutex-name row and the
`SeCreateGlobalPrivilege` row are closed the same way and **both name what is
still owed**: nothing in the suite has ever seen `Global\` creation actually
fail, so the refusal path is asserted and the condition that triggers it is not.

> ⚠️ **R3's row carries a warning about its own test, and it is the most
> transferable thing step 10 produced.** Written the intuitive way round — kill
> the holder, *then* open the mutex — the test observes a clean `Acquired`,
> because a named mutex is destroyed with its last handle and the next
> `CreateMutexW` makes a new one. That test passes against a build with no
> handling whatsoever. **A test for a crash-recovery path is worth exactly as
> much as the proof that it can fail**, and here the proof is an ordering that
> nothing in the code makes obvious.

**Build-order step 18 closed two, and added the second one on the way past.** The
4-part-version row is closed by **construction**: the version is derived from a
git tag and typed nowhere, so there is no place a fourth part could be written,
and a test fails the suite on any shape that is not three parts plus an optional
suffix. The row it added — a version string decorated with the commit sha,
against an updater that *matches* rather than compares — is a hazard this
repository imported from `SixFive7/FrameLink` rather than found, and it is closed
by an assertion on the **shipped attribute** rather than by the property that
sets it, because the property alone can be true while the mechanism is merely
un-provoked. It **names what is still owed**: FrameLink also greps every version
string in its linked binary, which needs a release script this repository does
not have yet.

**Closing a row is a claim about the product, not about the plan.** A section of this plan being written does not close anything; a section being *implemented and evidenced* might. That asymmetry is the reason this file outlives the rest.
