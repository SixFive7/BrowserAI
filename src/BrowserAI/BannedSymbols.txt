T:System.Console;stdout is the JSON-RPC protocol channel. Use StdioChannel for the wire and ILogger for diagnostics. MEASURED 2026-08-18 on .NET 10 with stdout redirected, which is exactly how an MCP client runs this: Console.OutputEncoding came back as code page 437 and Console.Out.NewLine as 0D-0A, and writing the two characters e-acute and a horizontal ellipsis put the bytes 82 2E on the wire - one character silently transcoded, the other replaced by a full stop. Console.OutputEncoding follows the machine's console code page even when nothing is attached, so on a machine set to 65001 the same code emits UTF-8; a wire format may not depend on that, which is why this is banned rather than configured. Console.In steals bytes the client sent as JSON-RPC, and Console.ReadKey throws InvalidOperationException on a redirected stdin - inside a catch that replaces the original exception with a new one.
T:System.Diagnostics.Debug;Debug.Assert does two different wrong things and neither is the one this ban used to claim. CORRECTED 2026-08-18 (previously 'raises a modal dialog on a machine with nobody at it, which is an invisible hang on a background MCP server') - that is .NET Framework's DefaultTraceListener and has not been true on .NET Core. Measured 2026-08-18 on .NET 10 with stdio redirected: a DEBUG build wrote 'Process terminated. / Assertion failed.' plus the message and a stack trace to stderr and DIED IMMEDIATELY with exit code 35, no dialog and no hang; a RELEASE build ran straight past it, because [Conditional("DEBUG")] compiles the call out. So the shipped artifact carries a guard that does nothing, and the suite carries one that kills the server mid-conversation. Throw, or log and carry on.
