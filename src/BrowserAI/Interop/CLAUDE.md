# `Interop\` — the whole P/Invoke surface

**All 47 `[LibraryImport]` declarations in the product are in these ten files, and nothing outside this directory calls Win32 at all** — *re-counted 2026-08-19 as lines matching `^\s*\[LibraryImport` under `src/BrowserAI/Interop/*.cs`, previously 43 in nine files; the four new ones are `GetDriveTypeW`, `QueryDosDeviceW`, `CreateFileW` and `GetFinalPathNameByHandleW` in `VolumeIdentity.cs`, which is how a session directory is judged a network path or an alias before anything opens it.* **The predicate is anchored deliberately, and scoped to `*.cs`** — *corrected 2026-08-18 (previously "as `[LibraryImport` attribute lines", which is not the predicate that produces the number)*: an unanchored grep over the same `.cs` files returns **49**, because `JobLauncher.cs` and `RestartManager.cs` each mention the attribute in prose inside a doc comment. *The scope half was corrected 2026-08-19: the stated predicate said "under `src/BrowserAI/Interop/`", and run against the directory rather than its `.cs` files it returns 55, because this very file discusses the attribute six times.* A re-count by the stated method returning a different number from the stated number is the failure this file exists to prevent, and it had already happened here. The rules below hold for every file here; each says what enforces it, and two of them are enforced by nothing.

- **Every declaration carries `[DefaultDllImportSearchPaths(DllImportSearchPath.System32)]`.** All **47** do, each one on the line immediately above its `[LibraryImport]` — *re-counted 2026-08-19 by the anchored predicate above, and counted independently rather than assumed to match: 47 anchored `[DefaultDllImportSearchPaths` lines against 47 anchored `[LibraryImport` lines. Previously "All 43", and "All 41" before that, which was already stale against the number in the sentence two lines above it.* **Nothing asserts it.**

  **The reason was wrong for 43 of the 47, and the rule survives untouched.** *(Re-counted 2026-08-19, previously "39 of the 43" and "33 + 5 + 1" below: the four new `VolumeIdentity` declarations are all `kernel32`, which is a KnownDLL, so they land in the class the attribute cannot change anything for. Nothing was re-measured — the per-library split is a count of this directory, and the measurement it rests on is about which libraries are KnownDLLs.)* *Corrected 2026-08-18 (previously "Without it a DLL of the same name sitting beside the executable wins the search, and the call you get is somebody else's".)* Measured 2026-08-18 with genuine `System32` copies of `kernel32.dll`, `user32.dll` and `rstrtmgr.dll` planted beside a probe executable: **without** the attribute, `kernel32`, `user32` and `ntdll` still loaded from `System32` and only **`rstrtmgr.dll` loaded from the application directory**; **with** it, `rstrtmgr.dll` loaded from `System32` too. `kernel32` and `user32` are **KnownDLLs**, resolved before any path search happens, and `ntdll` is mapped by the loader before user code runs — so for 37 + 5 + 1 declarations the attribute cannot change anything, and for the **4 `rstrtmgr.dll`** ones it is the whole difference ([kb](../../../kb/windows/processes.md#the-win32-interop-surface)). **Keep it on every declaration anyway**: it costs nothing, it is correct for the one library here that is not a KnownDLL, and the next library added may not be one either. **The trap is the audit rather than the rule** — anyone checking this by planting a fake `kernel32.dll` sees nothing happen and concludes the attribute is decorative.
- **A hand-written struct is checked against Microsoft's own metadata, or it is not written.** `InteropLayoutTests` is the oracle, reached through `CsWin32` and the names in `tests/BrowserAI.Tests/NativeMethods.txt`. **A struct added without a line in that file is unchecked and looks exactly like a checked one** — and this is the one defect class here that cannot present as an error: a field that slid four bytes makes `SetInformationJobObject` return success and do something else.
- **A process is `(pid, creationFileTime)`, never a bare pid; a browser is found by full image path, never by image name.** [`build/BannedSymbols.txt`](../../../build/BannedSymbols.txt) bans the framework's name-based calls and `NeverByImageNameTests` reads the tree for `taskkill /IM`, a WMI `Name` filter and a toolhelp `szExeFile` walk. **Neither can see a new native declaration added here**, which is exactly why this line is in this file: pids are reused within seconds, and the user has around forty `firefox.exe` of their own.
- **Half of that now has a mechanism, added because this file predicted the gap and the gap was already here.** `ProcessLivenessTests.EveryProcessHandleOpenedInTheProductIsPairedWithACreationTimeRead` reads `src/` for every `OpenProcess` **call** — the `[LibraryImport]` declarations are excluded, they have no handle to pair with — and requires a creation-time read within twenty-five lines of it. It was watched red at `8bf0e6c` against exactly the two sites that were wrong: `ClientLivenessWatcher.ForProcess`, which opened the pid from `InheritedFromUniqueProcessId` and held whatever answered, and `ProcessLiveness.ClientProcessName`, which wrote that stranger's image name into `browserai.json` as the client's identity. **What it still cannot see is the other half of the rule** — an image *name* comparison in a new declaration — and it cannot judge whether a pairing is the *right* one, only that one is there. Its `Pairings` list is the seam: adding a name to it is a claim that some new call establishes identity, and making that an edit somebody has to justify is the point.
- **Read `Marshal.GetLastPInvokeError()` before anything else runs.** **Nothing asserts this.** *Corrected 2026-08-18 (previously "A `Dispose`, a log call or an allocating `if` between the call and the read replaces the error with somebody else's" — which named the wrong culprit).* Measured 2026-08-18: the captured value **survives** a 5,000-append `StringBuilder`, a `GC.Collect()`, a `MemoryStream` round trip and a `Console.Out.Flush()`, and is destroyed only by a statement that **itself P/Invokes** — `File.Exists` on a missing path alone zeroed it ([kb](../../../kb/windows/processes.md#the-win32-interop-surface)). So an allocating `if` is safe and a log call that touches a file is not, which is the opposite of what the old sentence would have you audit for. **A second trap the old sentence hid entirely**: **12 of the 47** declarations here omit `SetLastError = true`, and for those `Marshal.GetLastPInvokeError()` returns a confident **0** rather than failing — a value that reads as success. *Re-counted 2026-08-19, previously "11 of the 43": the twelfth is `GetDriveTypeW`, which has no error to report — it answers `DRIVE_UNKNOWN` or `DRIVE_NO_ROOT_DIR` rather than failing — and it is still in this count because the rule is about what a reader may conclude from a zero, not about whether a particular call can fail.*
- **`AllowUnsafeBlocks` is on for P/Invoke declarations, never for hand-written pointer code.** Both project files say so in a comment; **nothing asserts it**, and the day it is used for anything else is the day this directory stops being a translation layer.
