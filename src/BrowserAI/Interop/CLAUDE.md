# `Interop\` — the whole P/Invoke surface

**All 43 `[LibraryImport]` declarations in the product are in these nine files, and nothing outside this directory calls Win32 at all** — *re-counted 2026-08-18 as lines matching `^\s*\[LibraryImport` under `src/BrowserAI/Interop/`, previously 41; the two new ones are `GetProcessTimes` and `CloseHandle` in `ClientLiveness.cs`, added with the identity pairing below.* **The predicate is anchored deliberately** — *corrected 2026-08-18 (previously "as `[LibraryImport` attribute lines", which is not the predicate that produces 43)*: an unanchored grep for `[LibraryImport` returns **45**, because `JobLauncher.cs` and `RestartManager.cs` each mention the attribute in prose inside a doc comment. A re-count by the stated method returning a different number from the stated number is the failure this file exists to prevent, and it had already happened here. The rules below hold for every file here; each says what enforces it, and two of them are enforced by nothing.

- **Every declaration carries `[DefaultDllImportSearchPaths(DllImportSearchPath.System32)]`.** All **43** do, each one on the line immediately above its `[LibraryImport]` — *re-counted 2026-08-18 by the anchored predicate above; previously "All 41", which was already stale against the 43 in the sentence two lines above it.* **Nothing asserts it.**

  **The reason was wrong for 39 of the 43, and the rule survives untouched.** *Corrected 2026-08-18 (previously "Without it a DLL of the same name sitting beside the executable wins the search, and the call you get is somebody else's".)* Measured 2026-08-18 with genuine `System32` copies of `kernel32.dll`, `user32.dll` and `rstrtmgr.dll` planted beside a probe executable: **without** the attribute, `kernel32`, `user32` and `ntdll` still loaded from `System32` and only **`rstrtmgr.dll` loaded from the application directory**; **with** it, `rstrtmgr.dll` loaded from `System32` too. `kernel32` and `user32` are **KnownDLLs**, resolved before any path search happens, and `ntdll` is mapped by the loader before user code runs — so for 33 + 5 + 1 declarations the attribute cannot change anything, and for the **4 `rstrtmgr.dll`** ones it is the whole difference ([kb](../../../kb/windows/processes.md#the-win32-interop-surface)). **Keep it on every declaration anyway**: it costs nothing, it is correct for the one library here that is not a KnownDLL, and the next library added may not be one either. **The trap is the audit rather than the rule** — anyone checking this by planting a fake `kernel32.dll` sees nothing happen and concludes the attribute is decorative.
- **A hand-written struct is checked against Microsoft's own metadata, or it is not written.** `InteropLayoutTests` is the oracle, reached through `CsWin32` and the names in `tests/BrowserAI.Tests/NativeMethods.txt`. **A struct added without a line in that file is unchecked and looks exactly like a checked one** — and this is the one defect class here that cannot present as an error: a field that slid four bytes makes `SetInformationJobObject` return success and do something else.
- **A process is `(pid, creationFileTime)`, never a bare pid; a browser is found by full image path, never by image name.** [`build/BannedSymbols.txt`](../../../build/BannedSymbols.txt) bans the framework's name-based calls and `NeverByImageNameTests` reads the tree for `taskkill /IM`, a WMI `Name` filter and a toolhelp `szExeFile` walk. **Neither can see a new native declaration added here**, which is exactly why this line is in this file: pids are reused within seconds, and the user has around forty `firefox.exe` of their own.
- **Half of that now has a mechanism, added because this file predicted the gap and the gap was already here.** `ProcessLivenessTests.EveryProcessHandleOpenedInTheProductIsPairedWithACreationTimeRead` reads `src/` for every `OpenProcess` **call** — the `[LibraryImport]` declarations are excluded, they have no handle to pair with — and requires a creation-time read within twenty-five lines of it. It was watched red at `8bf0e6c` against exactly the two sites that were wrong: `ClientLivenessWatcher.ForProcess`, which opened the pid from `InheritedFromUniqueProcessId` and held whatever answered, and `ProcessLiveness.ClientProcessName`, which wrote that stranger's image name into `lock.json` as the client's identity. **What it still cannot see is the other half of the rule** — an image *name* comparison in a new declaration — and it cannot judge whether a pairing is the *right* one, only that one is there. Its `Pairings` list is the seam: adding a name to it is a claim that some new call establishes identity, and making that an edit somebody has to justify is the point.
- **Read `Marshal.GetLastPInvokeError()` before anything else runs.** **Nothing asserts this.** *Corrected 2026-08-18 (previously "A `Dispose`, a log call or an allocating `if` between the call and the read replaces the error with somebody else's" — which named the wrong culprit).* Measured 2026-08-18: the captured value **survives** a 5,000-append `StringBuilder`, a `GC.Collect()`, a `MemoryStream` round trip and a `Console.Out.Flush()`, and is destroyed only by a statement that **itself P/Invokes** — `File.Exists` on a missing path alone zeroed it ([kb](../../../kb/windows/processes.md#the-win32-interop-surface)). So an allocating `if` is safe and a log call that touches a file is not, which is the opposite of what the old sentence would have you audit for. **A second trap the old sentence hid entirely**: 11 of the 43 declarations here omit `SetLastError = true`, and for those `Marshal.GetLastPInvokeError()` returns a confident **0** rather than failing — a value that reads as success.
- **`AllowUnsafeBlocks` is on for P/Invoke declarations, never for hand-written pointer code.** Both project files say so in a comment; **nothing asserts it**, and the day it is used for anything else is the day this directory stops being a translation layer.
