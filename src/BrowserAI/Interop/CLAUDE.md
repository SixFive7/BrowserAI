**It lives elsewhere because every rule below is a rule about Win32**, and not one of them applies to a third-party library compiled from vendored source: there is no Win32 metadata to check a struct against, no `SetLastError` to read, no image name to refuse -- and `System32` is the *wrong* search path for it, [measured 2026-08-26](../../../kb/windows/processes.md#system32-is-not-a-superset-of-no-attribute-and-the-module-cache-hides-it----measured-2026-08-26): a System32-only declaration cannot find a library beside the host at all. Putting it here would have meant writing an exception into each of these rules; the storage layer's declarations grow in that file instead. **The predicate is anchored deliberately, and scoped to `*.cs`** -- *corrected 2026-08-18 (previously "as `[LibraryImport` attribute lines", which is not the predicate that produces the number)*: an unanchored grep over the same `.cs` files returns **49**, because `JobLauncher.cs` and `RestartManager.cs` each mention the attribute in prose inside a doc comment. *The scope half was corrected 2026-08-19: the stated predicate said "under `src/BrowserAI/Interop/`", and run against the directory and not its `.cs` files it returns 55, because this very file discusses the attribute six times.* A re-count by the stated method returning a different number from the stated number is the failure this file exists to prevent, and it had already happened here. The rules below hold for every file here; each says what enforces it, and two of them are enforced by nothing.

- **Every declaration carries `[DefaultDllImportSearchPaths(DllImportSearchPath.System32)]`.** All **91** do *(re-counted 2026-09-25 after the move, 32 against 32, 42 against 42 and 17 against 17; previously **88**, 39, 32 and 17, and **85** that morning, 39, 29 and 17, then **80**, and **79** until Q294 b's broadcast)*, each one on the line immediately above its `[LibraryImport]` -- *re-counted 2026-09-24 and counted independently on each side: 39 against 39, 27 against 27, 13 against 13. Previously **78** at `db7210d`, and **59** before that day.* -- *re-counted 2026-09-15 across the three directories and counted independently on each side and not assumed to match: 37 against 37, 14 against 14, 8 against 8. Previously **51**, in one directory.* -- *re-counted 2026-09-15, and counted independently and not assumed to match: 51 anchored `[DefaultDllImportSearchPaths` lines against 51 anchored `[LibraryImport` lines. Previously **47**.* -- *The 2026-08-19 re-count read 47 against 47; "All 43" and "All 41" came before it, the second already stale against the number in the sentence two lines above it.* **Nothing asserts it.**

  **The reason was wrong for 47 of the 51, and the rule survives untouched.** *(Re-counted 2026-09-15 by library -- 39 `kernel32`, 6 `user32`, 4 `rstrtmgr`, 2 `ntdll` -- previously "43 of the 47", and "39 of the 43" and "33 + 5 + 1" before that. The four added that day are three `kernel32`/`user32` and one `ntdll`, all of them in the class the attribute cannot change anything for. Nothing was re-measured about the loader -- the per-library split is a count of this directory, and the measurement it rests on is about which libraries are KnownDLLs.)* *Corrected 2026-08-18 (previously "Without it a DLL of the same name sitting beside the executable wins the search, and the call you get is somebody else's".)* Measured 2026-08-18 with genuine `System32` copies of `kernel32.dll`, `user32.dll` and `rstrtmgr.dll` planted beside a probe executable: **without** the attribute, `kernel32`, `user32` and `ntdll` still loaded from `System32` and only **`rstrtmgr.dll` loaded from the application directory**; **with** it, `rstrtmgr.dll` loaded from `System32` too. `kernel32` and `user32` are **KnownDLLs**, resolved before any path search happens, and `ntdll` is mapped by the loader before user code runs -- so for 37 + 5 + 1 declarations the attribute cannot change anything, and for the **4 `rstrtmgr.dll`** ones it is the whole difference ([kb](../../../kb/windows/processes.md#the-win32-interop-surface)). **Keep it on every declaration anyway**: it costs nothing, it is correct for the one library here that is not a KnownDLL, and the next library added may not be one either. **The trap is the audit, not the rule** -- anyone checking this by planting a fake `kernel32.dll` sees nothing happen and concludes the attribute is decorative.
- **A hand-written struct is checked against Microsoft's own metadata, or it is not written.** `InteropLayoutTests` is the oracle, reached through `CsWin32` and the names in `tests/BrowserAI.Tests/NativeMethods.txt`. **A struct added without a line in that file is unchecked and looks exactly like a checked one** -- and this is the one defect class here that cannot present as an error: a field that slid four bytes makes `SetInformationJobObject` return success and do something else.
- **A process is `(pid, creationFileTime)`, never a bare pid; a browser is found by full image path, never by image name.** [`build/BannedSymbols.txt`](../../../build/BannedSymbols.txt) bans the framework's name-based calls and `NeverByImageNameTests` reads the tree for `taskkill /IM`, a WMI `Name` filter and a toolhelp `szExeFile` walk. **Neither can see a new native declaration added here**, which is exactly why this line is in this file: pids are reused within seconds, and the user has around forty `firefox.exe` of their own.
- **Half of that now has a mechanism, added because this file predicted the gap and the gap was already here.** `ProcessLivenessTests.EveryProcessHandleOpenedInTheProductIsPairedWithACreationTimeRead` reads `src/` for every `OpenProcess` **call** -- the `[LibraryImport]` declarations are excluded, they have no handle to pair with -- and requires a creation-time read within twenty-five lines of it. It was watched red at `8bf0e6c` against exactly the two sites that were wrong: `ClientLivenessWatcher.ForProcess`, which opened the pid from `InheritedFromUniqueProcessId` and held whatever answered, and `ProcessLiveness.ClientProcessName`, which wrote that stranger's image name into `browserai.json` as the client's identity. **What it still cannot see is the other half of the rule** -- an image *name* comparison in a new declaration -- and it cannot judge whether a pairing is the *right* one, only that one is there. Its `Pairings` list is the seam: adding a name to it is a claim that some new call establishes identity, and making that an edit somebody has to justify is the point.
- **Read `Marshal.GetLastPInvokeError()` before anything else runs.** **Nothing asserts this.** *Corrected 2026-08-18 (previously "A `Dispose`, a log call or an allocating `if` between the call and the read replaces the error with somebody else's" -- which named the wrong culprit).* Measured 2026-08-18: the captured value **survives** a 5,000-append `StringBuilder`, a `GC.Collect()`, a `MemoryStream` round trip and a `Console.Out.Flush()`, and is destroyed only by a statement that **itself P/Invokes** -- `File.Exists` on a missing path alone zeroed it ([kb](../../../kb/windows/processes.md#the-win32-interop-surface)). So an allocating `if` is safe and a log call that touches a file is not, which is the opposite of what the old sentence would have you audit for. **A second trap the old sentence hid entirely**: **21 of the 79** declarations here omit `SetLastError = true` -- *re-counted 2026-09-25 by the same predicate: **24 of the 85**, the three added that day being `SetForegroundWindow`, `ShowWindow` and `IsIconic`, which report nothing through the last error; and **27 of the 88** after the logon task's three ole32 calls, which answer an `HRESULT` and set no last error; still **27**, **of the 91**, after the scan's three overloads, which all set it* -- *re-counted 2026-09-24 by the same predicate, previously "13 of the 51"; one of the eight is `NamedPipes.GetCurrentProcess`, which answers a pseudo-handle and cannot fail, and the other seven were already in the tree, uncounted, before that day's change* -- -- *re-counted 2026-09-15 by the same predicate, previously 12 of 47. The thirteenth is the second `NtQueryInformationProcess` overload, which is `ntdll` and answers an `NTSTATUS` and does not set an error -- the three other declarations added that day all set it*, and for those `Marshal.GetLastPInvokeError()` returns a confident **0** instead of failing -- a value that reads as success. *Re-counted 2026-08-19, previously "11 of the 43": the twelfth is `GetDriveTypeW`, which has no error to report -- it answers `DRIVE_UNKNOWN` or `DRIVE_NO_ROOT_DIR` instead of failing -- and it is still in this count because the rule is about what a reader may conclude from a zero, not about whether a particular call can fail.*
- **`AllowUnsafeBlocks` is on for P/Invoke declarations, never for hand-written pointer code.** Both project files say so in a comment; **nothing asserts it**, and the day it is used for anything else is the day this directory stops being a translation layer.
