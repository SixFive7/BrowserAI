# `Sessions\` — one directory is one session

The directory is simultaneously the name, the handle and the lock, so everything here is a claim about **whose** directory it is. The rules below hold for every file; each says what enforces it, and the gaps are named as gaps.

⚠️ **Two files, and neither answers the other's question — 2026-08-26, previously one.** `browserai.lock` is the guard: it is written **once** at acquisition and never again, and its open handle is the whole of ownership. `browserai.data` is the record: every statement the session has made about itself and every call it has logged, as rows. They were one JSON file until this date, which is what made an append a whole-file durable rewrite and a rename — and what made an absence *undetermined*, a busy session periodically unheld, and a peer's transient handle able to refuse the writer's own re-open. **Every rule below that names `browserai.json` describes what a defect WAS**; the mechanism it names has moved, and where it has, the rule says so in its own words rather than being quietly re-pointed. See [`Storage\`](../Storage/CLAUDE.md) for the two files themselves.

- **A path is canonicalised once, by `CanonicalPath`, and every derived name comes from `SessionPath` on top of it** — the mutex, `browserai.lock`, `browserai.data`, the index key. ⚠️ *Corrected 2026-08-26 (previously "canonicalised once, by `SessionPath`").* They are two questions and were one member: *what does the filesystem call this* and *may this be a session directory*. Conflating them is why `browserai_list` had a path chain of its own — it must accept a volume root, which the second question refuses — and that second chain is where a listing through a junction answered *no sessions here* with no error at all. `CanonicalPathTests` covers the resolution against real aliases this machine builds; `SessionPathTests` covers the derived names. **Nothing stops a new caller canonicalising a path of its own**, and two components that canonicalise separately eventually disagree about one path — at which point two processes hold the same session.
- **The order inside `CanonicalPath` is load-bearing, and it is not an optimisation.** Characters first; then the object manager — `QueryDosDeviceW`, and `GetDriveTypeW` only on a letter that is not a substitution — with **no filesystem call in either**; then one directory open per level climbed. ⚠️ *Corrected 2026-08-26 (previously "`SessionDirectoryGuard` runs at `browserai_init` and `browserai_resume` only: the network question first … the alias question second").* An alias is **resolved** now rather than refused, the network is refused at **every** door, and `GetDriveTypeW` moved behind `QueryDosDeviceW` because on a `subst`ed letter it resolves the substitution and blocks: **21,035 ms**, measured 2026-08-26, then answering `DRIVE_NO_ROOT_DIR`. **Nothing stops a new caller putting a filesystem call in front of the network check** — and it would not fail anything: the refusal would still be correct, twenty-two seconds later, inside the per-directory gate where every peer waits. The one thing that would catch it is a clock, and [a clock cannot be honest here](../../../TESTING.md#every-duration-is-a-hang-detector-or-it-is-a-defect).
- **Compare two Windows paths by upper-casing both sides and then comparing ordinally**, or ask for `OrdinalIgnoreCase`. `SessionPath.Key` and `SessionManager.Beneath` do, and so does every path comparison in `src\` — checked, not assumed. **`CanonicalPathTests` now asserts it** (as `SessionDirectoryGuardTests` did before it), and that is a correction: *previously "**Nothing asserts it**", written 2026-08-17*, and between then and 2026-08-19 the same defect arrived twice more with the network/alias guard. **It reproduced this time.** `dotnet test` at `cc45900`: **482 passed / 2 failed from Git Bash, 484 passed / 0 from PowerShell**, same tree, same commit — because the working directory arrives as `c:\…` from one shell and `C:\…` from the other, while `GetFinalPathNameByHandleW`, `QueryFullProcessImageNameW`, `GetShortPathNameW` and `QueryDosDeviceW` all answer upper-case whatever started the process. The two assertions repaired at `b4c970a` rested on the mechanism and on a report; these rest on a red run.
  - **The mechanism is `DriveLetterCase`**, and eight tests in `CanonicalPathTests` are parameterised over it, so every path they compose is spelled both ways on every run. ⚠️ **And since 2026-08-26 it is not the only thing in play**: the product answers with the filesystem's own spelling now, which is always `C:`, so `ScratchRoot` anchors the suite's composed paths on that spelling too — otherwise every ordinal comparison in the suite would be a property of the invoking shell rather than of the product. The two are complements: this one removes an accidental dependence, `DriveLetterCase` keeps a deliberate one. The `Lower` arm composes a spelling **no Windows API ever returns**, so a comparison that is not case-insensitive is red on every machine and in every shell. Proof it works without choosing a shell: the planted arm failed *from PowerShell*, with the identical two failures Git Bash had produced.
  - ⚠️ **A single-shell run cannot see the shell-dependent form of this at all**, whoever runs it — which is why it was reported twice from a machine and never once from a build. *Corrected 2026-08-20 (previously "CI is `pwsh` end to end (`build.yml`), so CI cannot see the shell-dependent form of this at all"): the hosted CI that ran every step under `pwsh` was removed that day, and the property was never about CI.* The `Lower` arm is what puts it in front of any single-shell run; and since CI's removal [release checklist item 8](../../../RELEASING.md#8-run-everything) requires the suite to be run **from PowerShell and from Git Bash**, with both totals recorded, because the release gate is now the only gate there is.
  - **Eleven sites carried the shape and all eleven were test assertions; `src\` had none.** Eight in `SessionDirectoryGuardTests` (now `CanonicalPathTests`), one each in `HeadlessBinaryTests`, `StraySweepTests` and `SessionPathTests`. ⚠️ *Corrected 2026-08-26 (previously "The one deliberate ordinal path comparison in the product is `ArtifactRouting.PrefixOf`, which separates names the product generated from names a caller chose — a genuinely case-sensitive question").* That type is deleted with the whole of artifact routing, so **there is no deliberate ordinal path comparison left in the product at all** — which makes the rule above unconditional rather than one-with-an-exception, and makes the next one somebody adds worth arguing for out loud.
- **Two tool calls can name one session at the same moment, so `SessionLock` is thread-safe about its own lifetime**: `Append`, `Settle`, `SettleOpening`, `AppendPurpose`, `ReleaseAndDelete` and `Dispose` each hold `SessionLock._inProcess` — a private in-process `Lock`, not a fourth [scope](LockScopes.cs) — for their whole body, and every caller delegate they invoke runs inside it. It carries a second job since the store arrived: `Append` is an `INSERT` followed by `last_insert_rowid` on **one** connection, and two threads interleaving there would hand one call the other's row id, after which a settle lands on somebody else's entry. `SessionLockTests.ADisposalArrivingDuringAReleaseAndDeleteWaitsForItInsteadOfLeakingTheHandle` and `.AMutationArrivingDuringAReleaseAndDeleteWaitsForItRatherThanReadingAFieldItIsWriting` force two of the three interleavings through the one caller delegate this class still has. ⚠️ **The third — a disposal arriving during a MUTATION — has no deterministic seam left and is named as a gap rather than implied**: a mutation runs no caller code, so nothing can watch that pairing interleave, and what holds it is the same `Lock` the other two prove both disposal paths and every writing path take. *Corrected 2026-08-26 (previously `Rewrite` and a test that forced the disposal through its `update` delegate).* **Nothing stops a new mutating path being added that does not take it**, and the shape it would have is the one that was there: a `_disposed` check outside the exclusion, which is a decision taken by reading a field another thread is writing.
- **A holder is `(pid, creationFileTime)`, never a bare pid.** `LockFileTests` and `SessionLockTests` cover the guard and the reclaim path. **Nothing stops new code reading `ProcessId` on its own** — and a pid alone reclaims a live session's directory the moment Windows reuses the number.
  - ⚠️ **Re-taking our own guard is a different event from a reclaim, and it was logged as one until 2026-08-30.** `destroy` and `set_purpose` both dispose the live session and re-acquire, so the guard on disk names the very process about to take the directory — and `SessionLog.Reclaimed` said *"previous holder was PID n, still running: True"* about it. True word by word; read by anyone scanning the log as a live stranger being evicted, which is the one event on this path worth waking up for. **It was very nearly every reclaim that file has carried since the 2026-08-26 logging cutover** — counted 2026-08-30, predicate quoted: **8,423** `Session lock reclaimed` lines, **8,418** of them `still running: True`, **zero** `Session lock acquired` lines, and in the two 2026-08-29 files alone **2,081 of 2,081** — because a machine-wide record can only hold those two paths and both are structurally never `Fresh`. The five that are not self-retakes are reclaims from a holder that had died, which is what keeps the discriminator from being vacuous. `SessionLog.ReacquiredOurOwnGuard` is its own event id now, chosen on `(pid, creationFileTime)` against the holder this acquisition just wrote, so a stranger wearing our number still reads as the takeover it is. **`SessionLockOutcome` deliberately did not move** — the directory *was* held and *is* now ours, so a caller branching on the outcome is right to see no difference — and `SessionLockTests.AProcessReTakingItsOwnGuardSaysSoRatherThanReportingAReclaim` asserts the record while `.AHeldLockRefusesASecondWriterAndStillAnswersAReader` goes on pinning the outcome. **Nothing stops a new caller logging both**, which is exactly why that test's second arm refuses the old sentence anywhere in the capture rather than merely requiring the new one.
- **Attribution may fail; detection may not.** `StraySweep` ends only what it can tie to both an image path BrowserAI owns and a window title it can read. Anything it cannot attribute is **reported loudly by full path and left running** — never terminated on a guess, never silently dropped. `StraySweepTests` holds the shape of this; the judgement about a new candidate kind is yours.
- **`browserai.data` is append-only: every field is an ordered list of timestamped statements, and nothing is ever overwritten.** `SessionLock.Compose` is the only way a field gains one at acquisition and `AppendPurpose` the only way afterwards; both append **only when the value changes**, except `holder`, which dedup cannot bound because `(pid, creationFileTime)` never repeats. `SessionRecordTests` covers the dedup and the absence of eviction. ⚠️ *Corrected 2026-08-26 (previously "`LockRecord.Append` … trims out of the **middle** so the first statement — the one `Created` is read from — survives", with `LockRecordTests` covering "the dedupe, the cap and the trim").* **There is no cap and there is no trim**: nothing evicts, so `Created` is the oldest statement because it is still there rather than because a policy protected it — and a `purpose` is a row per change, which is what killed `resume`'s concatenation and the silent truncation that came with it at 2,000 characters. **The rule this exists to serve is the one nothing can enforce: a session says how it got here, so BrowserAI never has to ask a caller to confirm what it already knows.** That is what deleted `acknowledgeCopy`, and the product now has zero confirmation flags — `ModelSurfaceTests.NoAuthoredToolAsksTheCallerToConfirmAnything` counts them, and cannot tell you that a new refusal *should* have been a returned fact.
- **A sharing violation on `browserai.lock` may be read as *owned*; nothing else may be read as *free*.** `SessionLock.ProbeForHolder` refuses in front of the per-directory gate on that one answer and falls through to the gate on every other — absent, denied, unparseable, or an open that succeeded. `SessionLockTests.AProbeThatFindsTheDirectoryFreeStillProvesItAtTheGate` fails if the free path ever skips the gate. **Nothing stops a new caller adding a second pre-gate shortcut**, and the one that would be added is the tempting one: with the gate skipped on the free path both contenders probe free, the rename retry loop becomes the serialiser, and the loser takes the name off a live holder's still-open handle.
  - **There are two callers since 2026-08-20 and exactly one opener.** `SessionLock.ProbeLiveness` is the open — one `CreateFile` on the guard, **never a database open**: a store open is orders of magnitude dearer, it can leave a `-shm` in a directory nobody asked it to touch, and the newest holder statement cannot answer *is anybody still holding this* anyway. `ProbeForHolder` is a *decision* built on it and `browserai_list` is a *report* built on it, so the rule above is stated once rather than twice. The report is three-valued — **in use: YES / no / UNKNOWN** — and `SessionListTests` holds all three. ⚠️ *Corrected 2026-08-26 (previously the absent-guard arm "is `Undetermined` and never `NotHeld`", and the report went through `ProbeLivenessUnderTheGate`).* **An absent guard is now genuinely free, and the gate is gone from this path**, because the file is written once and never rewritten — an absence was *undetermined* only while a record was being replaced as often as it was read. The window that is left is between a peer's rename and its own first hold, inside the gate, once per session; `SessionListTests.APeerInsideCreateOrTakeIsTheOneWindowTheListingCanStillMisreport` pins it rather than leaving it to be discovered. ⚠️ **The report names no holder, and that is the rule the listing adds rather than inherits:** a sharing violation says the file is held and never by whom, so *"held by PID n"* on every entry would publish the wrong sentence below on every listing instead of once in a refusal. `SessionListTests.ListSaysWhichSessionsAreInUseAndNeverPrintsCouldNotTellAsFree` asserts that absence. **Nothing stops a new caller printing the record's pid beside the probe's answer** — the two are read from different things and only one of them is current.
  - **The probe cannot be made harmless, and 2026-08-19 is when that stopped being theory.** To be refused by a holder's `FileShare.Read` it must ask for access outside `Read`, and a handle whose granted access is outside `Read` is exactly what an open sharing only `Read` is refused by — *detecting an owner and blocking one are the same capability*, so no share mode dissolves it. CI run 32203064556 attempt 1 caught the consequence: a peer probing in the microseconds between a writer's rename and that writer's re-open refused the re-open, and two processes' holder statements ended up in one record. The absorption is on the gated side and its licence is a precondition rather than a guess: `RenameWindow.WaitOutWhereNoOwnerIsPossible` may wrap a hold **only** where the caller holds the gate and the file on disk already names it, because becoming an owner means passing through `TakeOrReport`, which needs that gate. `SessionLockTests.TheOnlyOpenThatWaitsAHandleOutIsTheOneThatFollowsOurOwnWrite` holds which opens qualify — and it asserts the *pairing* rather than a list of names, so an open that waits without a write above it is a red build. *Corrected 2026-08-26 (previously `SessionLock.ReopenHeld` against `OpenHeld`, neither of which exists).* **The two that do not are ownership tests and must never be widened into it** — waiting a live owner out for thirty seconds and then calling it a peer looking is the mechanism inverted, and one of those two still reads a peer's probe as `Contended`, which is [its own hazard row](../../../HAZARDS.md#hazard-index).
- **Which tools this build forwards is a FILE, not code.** [`tool-verdicts.json`](../../../tool-verdicts.json) carries one row per tool — `allow`, `deny` with the reason a caller reads and the date it was judged, or `answer` — and `ToolVerdicts` is the only thing that reads it. **Deny by default:** a name with no row is refused at the door and never reaches a child. `ToolVerdictTests` compares the file with the golden snapshot in both directions and refuses fifteen malformed shapes; `SessionPolicyTests` drives the door and the advertised list through rig copies of the file, so the product's own deny set stays at exactly one. ⚠️ *Added 2026-08-26, replacing `SessionToolPolicy` — a denylist of one name whose reasoning was a doc comment nothing downstream could read.* **Nothing stops a new caller adding a second by-name refusal in C#**, and it would pass every test here: what the file buys is that the judgement is reviewable beside the payload it judges, and a refusal written inline is invisible to that.
  - ⚠️ **That was true of the `upstream` half and NOT of the `authored` half, and the row said it of both.** *Added 2026-08-26.* `SessionToolSurface.IsAuthored` short-circuited every `browserai_` name before the verdict door, and `SessionToolSurface.Rewrite` advertises the seven authored tools from `SessionToolSurface.Names` rather than from the file — so deleting an `answer` row changed nothing a caller could observe, and their whole role was build-and-test-time. `ToolVerdictTests.TheAuthoredRowsAreExactlyTheToolsBrowserAiAnswersItself` holds them identical to that surface in both directions, and the file carries the same sentence about itself so a reader meets it where the rows are.
    - ⚠️ **The short-circuit is an EXACT match since 2026-08-26 (later the same day), so the `answer` rows are load-bearing at run time too.** It was a *prefix* test, so `browserai_zzz` never reached the verdict door: it landed on `SessionManager.InvokeAsync`'s default arm, was refused with a good sentence, and **wrote no log row**, because no session had been resolved at that point — while an unjudged *upstream* name was recorded on the session it named. Same class of caller mistake, two different records. Now both are deny-by-defaulted at the door and both land in the log. `SessionPolicyTests.AnUnjudgedAuthoredNameIsRefusedAtTheVerdictDoorAndRecordedOnItsSession`, watched red on the session manager's own sentence coming back instead of the verdict door's. ⚠️ **The residual is stated rather than closed**: with no resolvable session there is nowhere to write a row and there cannot be, which is the same reason the session-missing and unknown-session refusals go to the machine-wide log. The same arm asserts that half — **and asserts what the answer is**, because the exact match briefly made it wrong. A `browserai_` name that is not one of the seven, arriving with no session, was answered *"this needs a `session`"*, which sends a caller to supply one for a tool that does not exist; it gets `SessionToolSurface.NotOneOfOurs` instead, which names the seven that do. That is what `IsInTheAuthoredNamespace` is for — the prefix question is still asked, in the one place that genuinely needs the wider one, under a name that says which question it is. **It was caught by `ReinstallBrowserTests.EveryAuthoredToolIsAnsweredAndAnUnknownOneIsRefused`, not by review.**
- **A refusal is a sentence the model reading it can act on, and it lives in `SessionErrors`.** `ErrorCatalogueTests` proves every catalogue entry is reachable from a real path. **It cannot tell you that a refusal you wrote inline belongs in the catalogue**, which is the only way this rule is ever broken.
- **A wrong JSON type is a named refusal and never `-32603`.** `name`, `session` and `why` are the three strings a caller chooses, and they are kind-checked at the door in `BrowserProxy.Text`. The shape that shipped — `(node as JsonValue)?.GetValue<string>()` — does not answer `null` on `"name": 5`: `JsonValue` accepts a number and `GetValue<string>` throws `InvalidOperationException`, which escaped the handler and reached the caller as a bare internal error with the SDK's own wording, telling a model that BrowserAI broke when what happened is that it sent a number. `SessionPolicyTests.AWrongJsonTypeOnNameSessionOrWhyIsANamedRefusalAndNeverAnInternalError` covers all three plus a positive control. **Nothing stops a fourth caller-supplied string being read the old way.**
- **A refused call is recorded, and a call BrowserAI could not record is not forwarded.** Both halves are `browserai.data`'s, and the second is why `SessionLock.Append` throws rather than swallowing. ⚠️ *Corrected 2026-08-26 (previously refusals went to `browserai.log` and the record held only forwarded calls).* That file is gone, so the record is the only place *the agent reached for a tool this build will not forward* survives at all — which makes it replay rather than diagnostics. `SessionLogTests.ARefusedCallIsRecordedAsAFailedRowCarryingTheRefusal`.
