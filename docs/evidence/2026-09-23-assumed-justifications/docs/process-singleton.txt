VERBATIM, the receiving end (lines 142-165, ProcessLaunchNotification): the message window
handles WM_COPYDATA, runs ParseCommandLine over the COPYDATASTRUCT and hands the resulting
base::CommandLine and current_directory to notification_callback.Run(...).

WHAT THIS ESTABLISHES, exactly: the singleton is keyed on the USER DATA DIRECTORY, the
existing instance advertises that directory as a message-window title, and a second launch
naming the same directory has its command line delivered to the running browser over
WM_COPYDATA instead of starting a browser of its own. So the row's mechanism is real and its
trigger is precise: it is the shared user-data-dir that forwards, which is why `channel:
"chrome"` (whose fallback profile is %LOCALAPPDATA%\Google\Chrome\User Data) reaches the
operator's own browser and a per-session profile under a BrowserAI directory cannot.

NOT ESTABLISHED and not claimed: nothing here was run against a live Google Chrome on this
machine -- no probe drove a second launch at the user's own profile, deliberately, because
doing so is the thing the decision exists to prevent.
