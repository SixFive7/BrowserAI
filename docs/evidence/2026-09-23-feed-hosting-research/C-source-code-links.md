# "Source code (zip)" / "Source code (tar.gz)" on a GitHub release — the evidence

Read 2026-09-23.

## The documented behaviour

docs.github.com/en/repositories/releasing-projects-on-github/about-releases, verbatim:

> "GitHub will automatically include links to download a zip file and a tarball
> containing the contents of the repository at the point of the tag's creation."

"automatically include", with no accompanying setting, flag or opt-out anywhere
on that page.

docs.github.com/en/repositories/working-with-files/using-files/downloading-source-code-archives,
verbatim:

> source code archives are "generated by the `git archive` command in one of two
> formats: tarball or zipball."
> "An archive of a commit ID will always have the same file contents whenever
> it's requested…"
> "The exact compression settings used to generate a zipball or tarball may
> change over time… GitHub will give at least six months' notice before changing
> compression settings."

## The REST API has no parameter for it

docs.github.com/en/rest/releases/releases, read 2026-09-23.

`POST /repos/{owner}/{repo}/releases` (Create a release) body parameters, complete:
`tag_name` (required), `target_commitish`, `name`, `body`, `draft`, `prerelease`,
`discussion_category_name`, `generate_release_notes`, `make_latest`.

`PATCH /repos/{owner}/{repo}/releases/{release_id}` (Update a release) body
parameters, complete: `tag_name`, `target_commitish`, `name`, `body`, `draft`,
`prerelease`, `make_latest`, `discussion_category_name`.

**Neither list contains anything that controls, hides or removes the source
archives.** `zipball_url` and `tarball_url` are *required* response fields
(`string or null`).

## They are not release assets, so "Delete a release asset" cannot reach them

Measured on this repository, `gh api repos/SixFive7/BrowserAI/releases/tags/v1.1.0`:

```json
{"assets":["assets.win.json","BrowserAI-1.1.0-manifest.zip","BrowserAI.app-1.1.0-full.nupkg",
           "BrowserAI.exe","BrowserAI.zip","RELEASES","releases.win.json"],
 "assets_count":7,
 "tarball_url":"https://api.github.com/repos/SixFive7/BrowserAI/tarball/v1.1.0",
 "target_commitish":"master",
 "zipball_url":"https://api.github.com/repos/SixFive7/BrowserAI/zipball/v1.1.0"}
```

The source archives are **top-level URL fields, not members of `assets[]`**. Every
asset-management endpoint (`DELETE /releases/assets/{asset_id}`, `gh release
delete-asset`) operates on `assets[]` only, so there is nothing to delete.

## Tags versus branches — no difference

docs.github.com/…/about-releases: *"Releases are based on Git tags, which mark a
specific point in your repository's history."* `target_commitish` only names what
a **new** tag is created from. Measured above: v1.1.0 carries
`target_commitish: "master"` and its archives are keyed
`…/zipball/v1.1.0` — the **tag**. A release is never keyed on a branch, so there
is no branch-vs-tag distinction to exploit.

## Private repositories — no documented difference found

The REST schema above is one schema for all repositories and carries no
visibility-conditional parameter, and the feature-request threads below are
raised by enterprise/private users as well as public ones. **I looked for a
statement distinguishing private from public repositories on this point and did
not find one; that is an absence I searched for rather than a proven negative.**
For a private repository the archive URLs exist identically and inherit the
repository's own access control — the links are still rendered on the release
page to anyone who can see the release.

## GitHub's own statement

[community/discussions/6003](https://github.com/orgs/community/discussions/6003),
*"No way to disable auto-generated source code zip links"* — the only GitHub
staff reply, **MylesBorins, 2021-10-06**, verbatim:

> "This is a great idea and something we've talked about internally. We would
> need to do some research to see if there are any systems that rely on these
> artifacts that would break in fun and mysterious ways before we could follow
> through on this. I've created a feature request internally. We are looking at a
> number of improvements that we could make to artifacts / assets, but we may not
> be funding this effort in the immediate future (to set expectations)"

Still open, with comments as recent as April 2026. Related, all open:

- [#89928](https://github.com/orgs/community/discussions/89928) — *"Feature Request: Add ability to hide 'Source code' assets on a release"*, opened 2024-01-20 by @pboushy, **0 replies**, marked Unanswered.
- [#166048](https://github.com/orgs/community/discussions/166048) — *"Feature request: Disabling auto-generated download archives"*, opened 2025-07-14 by @solemnwarning, **unanswered**. Quote: *"I would like to be able to disable the 'Download ZIP' button on the repository home page, and disable/replace the 'Source code' assets on the releases"*.
- [#158761](https://github.com/orgs/community/discussions/158761) — same request, bot acknowledgement only.

## Supported settings that change what the links CONTAIN (not whether they appear)

1. **`.gitattributes` `export-ignore`.** GitHub documents the archives as
   *"generated by the `git archive` command"*; git-scm.com/docs/gitattributes,
   verbatim: *"Files and directories with the attribute `export-ignore` won't be
   added to archive files."* ⚠️ **This is a doc-to-doc inference, not a
   measurement** — GitHub's own pages never state that they honour
   `export-ignore` for release zipballs, and nothing here was tested against a
   real archive. Taken to the limit it would produce a near-empty zip, which is a
   worse artifact than the real source rather than a removal.
2. **"Include Git LFS objects in archives"**, a repository setting
   ([docs](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/managing-repository-settings/managing-git-lfs-objects-in-archives-of-your-repository)).
   Default is pointer files only; enabling it embeds the objects and charges the
   downloads against the account's LFS bandwidth. Not applicable — this
   repository uses no LFS.
3. `export-subst` (git-scm.com/docs/gitattributes) substitutes commit
   placeholders inside archived files. Cosmetic.

**Nothing changes whether the two links appear.**
