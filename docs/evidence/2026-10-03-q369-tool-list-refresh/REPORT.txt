## The plain answer

**Claude Code (CLI 2.1.288 and the VS Code binary 2.1.287, identical in every arm): it works, on two conditions.** BrowserAI must declare `capabilities.tools.listChanged: true`; today it answers `"tools":{}` (`BrowserProxy.cs:340-346` on origin/next), and then Claude Code ignores the notification (9 of 9). And the process that handed out the placeholder must be the one that sends the notification. Then Claude Code re-lists at once in `-p`, in the VS Code transport and in the terminal UI (18 of 18), and the model can call a real tool on its next request, inside the same turn in `-p`. Two things stay for the rest of the session: the placeholder tool (still offered to the model; calling it gets Claude Code's own "No such tool available ... does not offer this tool here") and the placeholder's server instructions (87 of 87 sessions that started on a placeholder).

**If the update ends that process**, which Velopack does to every server that started before the swap, the session keeps the placeholder. `-p` and VS Code start the server again on the next call, but never re-list a server they re-launch that way, and a list_changed the re-launched server sends right after `initialize`, or 1.5 s later, changes nothing (0 of 18). The terminal UI does not re-launch at all: it lists the server as failed and refuses the call itself (9 of 9). **A person** then has to reconnect: terminal `/mcp`, browserai, Reconnect (real tools 18 of 18); VS Code's "MCP servers" dialog, Reconnect, or Disable then enable (24 of 24, driven through the control requests the extension sends); or a new conversation. **A model cannot**: 2.1.288 contains a `RefreshMcpTools` tool, but it was offered in none of 27 sessions with the default tools on.

**Codex (0.155.0-alpha.9.2 and 0.160.0, exec and app-server): no.** It ignores list_changed in every arm (30 of 30) and keeps the list a thread's connection took when it started. Only a new connection replaces it: a new thread (6/6), a working-directory change (TUI `/cd`, app-server `thread/settings/update`, 6/6), or a new process (`exec resume --last`, 18/18). `config/mcpServer/reload` leaves a live placeholder in place (6/6) and helps only once the process is dead or failed (12/12). A model cannot refresh.

**For the case Q369 is about**, a server started during an apply and killed by it, the placeholder leaves Claude Code `-p` and VS Code sessions worse off than today's real list: with the real list the same kill heals by itself on the next call (PBr 3/3, SBr 6/6).

## What the model receives, and how each client shows it

The "model" is a script, so what a real model would do with these texts is not measured. What it would receive is captured byte for byte (`runs\model-texts.txt`):
- **Claude Code tool entry**: name `mcp__browserai__update_in_flight`, the server's description unchanged, `input_schema` `{"type":"object","properties":{},"additionalProperties":false}`.
- **Claude Code server instructions**: in a role `system` message, "# MCP Server Instructions / The following MCP servers have provided instructions for how to use their tools and resources: / ## browserai / <instructions>".
- **Claude Code call result**: `content:[{"type":"text","text":"<the server's text>"}]`; a server `isError` result arrives as the plain string with `is_error: true`, no wrapper. After a refresh, a call to the placeholder: `<tool_use_error>Error: No such tool available: mcp__browserai__update_in_flight. Its MCP server 'browserai' is connected but does not offer this tool here. Continue without it.</tool_use_error>`.
- **Claude Code with tool search on** (the first-party default; a custom `ANTHROPIC_BASE_URL` turns it off, so those runs forced `ENABLE_TOOL_SEARCH=true`): the model sees only the name in a deferred-tools list until it calls ToolSearch. After the refresh it is told "The following deferred tools are now available via ToolSearch ... mcp__browserai__browserai_init, mcp__browserai__browserai_list" and "The following deferred tools are no longer available (their MCP server disconnected). Do not search for them ...: mcp__browserai__update_in_flight". So up front the name and the instructions carry the message, and the description only after a ToolSearch.
- **Codex**: a namespace `mcp__browserai` whose description is the server instructions, holding `update_in_flight` with its description. Output: `[{"type":"input_text","text":"Wall time: 0.0158 seconds\nOutput:"},{"type":"input_text","text":"<the server's text>"}]`. After a kill: "tool call error: tool call failed for `browserai/update_in_flight` / Caused by: / Transport closed".

How each client shows it:
- **Claude Code terminal**: the call collapses to "Called browserai"; ctrl+o shows "browserai - update_in_flight (MCP)" with the text under it; an isError result shows "Error: <text>". `/mcp` lists "browserai 1 tool"; the server menu shows Status connected, Tools: 1 tool, View tools / Reconnect / Disable, and View tools lists `update_in_flight`. After the notification: "2 tools", nothing announced. After a kill: failed, with Reconnect / Disable.
- **VS Code**: not opened (no window). What its webview receives: the stream-json tool_use and tool_result, a new `system/init` at the next turn listing the new tools, and `mcp_status` (the data its MCP dialog shows): "connected: update_in_flight" before, "connected: browserai_init, browserai_list" after a refresh. After a kill it still reports connected with the placeholder.
- **Codex**: `exec --json` emits `item.completed` `mcp_tool_call` with the result content, status "completed", or "failed" for an isError result or a transport error. The app-server emits `item/completed` `mcpToolCall` the same way and `mcpServer/startupStatus/updated` starting / ready / failed. A host using the plain status list shows the real tools while the thread's model still has the placeholder (24 of 24).

## Directions for Q369

**Primer.** An apply ends every process under the install root with `TerminateProcess(handle, 1)`, in two passes, the second just before the swap (`kb/packaging/velopack.md`, measured 2026-09-24: servers started up to about 2.5 s into the apply were killed, later ones ran the new version). A server a client starts in that window is killed if it started before the swap. What the client is left with depends on whether the kill lands before or after the server finished its handshake. Q369 is about that: Q296 c makes the handshake wait for the Playwright child, so more of those kills land before it finishes. Measured today:
- Killed before the handshake finished: every client records a failed server. `-p` and VS Code: zero BrowserAI tools for the session, no retry (PK 3/3, SK 6/6). Terminal: failed until Reconnect (TK 3/3). Codex: failed until a reload or a new thread, or a resume for exec (AK 6/6, XK 6/6).
- Killed after it, holding the real list: `-p` and VS Code heal on the next call and the model never sees it (PBr 3/3, SBr 6/6). Terminal: failed until Reconnect (TBr 3/3). Codex: Transport closed until a refresh (AB 6/6, XB 6/6).
- Killed after it, holding a placeholder: `-p` and VS Code keep the placeholder until a person reconnects (0/18 re-lists). Terminal and Codex as above.

| | Handshake during an apply | Server killed after the handshake: `-p` / VS Code | Not killed: Codex | Cost |
|---|---|---|---|---|
| A. Keep Q296 c, declare `listChanged` | waits for the child | heals on the next call | real list | one capability line and a test |
| B. Placeholder as posed | milliseconds | stuck on the placeholder until a person acts | placeholder for the whole thread | stale tool name and instructions in every Claude Code session it touches |
| C. Real list from this version's own copy, child started after the updater | milliseconds | heals on the next call | real list | an exception to "schemas come from the child at run time", a fallback, a test |
| D. Hold the handshake until the updater has gone | the whole hold | the hold is pre-handshake, so a kill is a failed start | real list | small |
| E. A relay outside the install root | not exposed to the kill | the client never sees the kill | real list | the largest change; Q254 reversed |

- **A. Keep Q296 c and add `tools.listChanged: true`.** No behaviour change for a client that never gets a notification, and BrowserAI's own Q261 notification (`BrowserProxy.cs:630`), which Claude Code cannot honour today, starts working on first connections. Q369's window stays as accepted under Q286 b.
- **B. The placeholder as posed** (`update_in_flight`, `listChanged`, list_changed once the updater has gone). Shortens the handshake to milliseconds. Works only in Claude Code and only for a server that survives the apply, which means one started after the swap. A server started before the swap is killed anyway, and the placeholder turns today's self-healing post-kill state into a stuck one in `-p` and VS Code; Codex keeps the placeholder for the whole thread even when nothing is killed.
- **C. Serve this version's real list without the child during an apply, and start the child once the updater has gone.** Same short handshake as B with a valid list, so a post-kill re-launch heals in `-p` and VS Code and Codex gets the real tools. Two possible sources: a copy the server writes from the child's `tools/list` on every normal start, or the golden snapshot the payload already carries and `UpstreamSnapshotTests` holds against the child. Needs the maintainer's exception to "schemas come from the child's `tools/list` at run time" for the apply window, a fallback when the copy is missing (start the child, as now), and a test. The client half is measured (PBr, SBr, the 2026-09-25 Q296 runs); the server half is neither built nor measured.
- **D. Hold the handshake until the updater has gone** (Q296's alternative e, measured 2026-09-25 to work for holds of 1.3 to 2.8 s). Simple, but every kill inside the hold is a kill before the handshake, which is the failed start Q369 wants fewer of.
- **E. Take servers out of the kill pass**: a relay outside the install root as the registered command (Q254's direction not taken; measured 3/3 in both clients on 2026-09-24). The client's pipe survives the swap, so no client ever sees a kill, and a refusal or placeholder from the relay needs no refresh. The at-least-once re-send that priced the relay out does not arise for calls refused during an apply. Cost: a second binary outside the root, and Q254 reversed.

**Recommendation: A now, and C as the answer to Q369's window if the maintainer accepts the exception; not B.** A is needed for any notification to work in Claude Code and costs one line. C keeps the placeholder's speed and drops its cost. If C is declined, keep Q296 c and accept the window as Q286 b did: no measured client is better off with B.
