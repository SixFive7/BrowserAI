A theory nobody had ever run, a cliff four kilobytes wide, and the one number that would not come out

WHAT WAS RUN. QUESTIONS.md section 8 -- the silent Chromium death -- had been
open for nine days across three sightings and one recurrence that diagnosed
itself down to a five-line browser log, and it ended on the sentence "Nobody has
run that". That sentence is now false. Direction (b) ran on 2026-08-27, aimed at
desktop heap, and the verdict is REPRODUCED DIFFERENTLY: every element of the
2026-08-26 shape comes out except the exit code.

THE RIG, AND WHY IT COULD NOT TOUCH THE SESSION. A desktop of its own is created
inside WinSta0 with CreateDesktopW. Each desktop gets its own heap allocation,
and GetUserObjectInformationW with UOI_HEAPSIZE says this one got 20,480 KB --
the identical figure to the default desktop -- so the rig desktop is the
interactive desktop's equal in size and entirely separate in fact. One filler
process launched onto it through STARTUPINFO.lpDesktop spends that heap, and the
provisioned Chromium is then launched onto the same desktop with the sweep
test's own command line, both pipes drained to end of file. No registry key was
touched, no SharedSection was changed, and the interactive desktop still reads
20,480 KB afterwards. Window TEXT lives in the desktop heap, which is the lever
that made this cheap: 4,637 message-only windows carrying a 2,048-character
title spend the whole 20,480 KB in 2.7 seconds and 4,640 USER handles, inside
the 10,000-object per-process quota.

WHAT MATCHED, POINT BY POINT. Eight launches onto a heap spent to the byte,
against sixteen healthy controls on the same desktop before and after. Nothing
on stdout and nothing on stderr, both drained to end of file, 8 of 8. The
browser's own log stops at the same five lines in the same order, ending at
scheduler_loop_quarantine_config.cc:195, in 6 of 8 -- the other two carry one
further webrtc_event_log_manager.cc:126 line. Zero Chrome_MessageWindow of any
title, 8 of 8, against five in every one of the sixteen controls, one of them
titled with the profile path. GetPerformanceInfo reporting 430 processes,
262,355 handles and 66% of RAM free: the same clean bill of health as the wild
capture, on a machine that is out of the one resource.

THE THRESHOLD IS A CLIFF, AND THE SILENCE BELONGS TO ITS LAST FOUR KILOBYTES.
Three launches at each level. 4,637 windows held and the browser dies 8 of 8
with nothing on either stream. 4,636 -- about 4.4 KB free -- and it still dies
3 of 3, but with 61 to 63 log lines and 440 bytes of stderr, having reached its
GPU child. 4,635 and it dies 2 of 3. 4,634, about 13.2 KB free, and it lives 3
of 3 with 678 log lines; so does every one of eight further levels down to 3,600
windows and 4.6 MB free. So the shape recorded in the wild belongs to a heap
spent to the byte and to nothing less, which is a far more specific claim than
"the browser died when something was tight".

WHAT DID NOT MATCH, SAID PLAINLY. The wild exit code was 1. Across four
exhaustion regimes and 28 deaths the rig produced two codes and never a 1:
0x80000003 where the heap was simply full, and 0xE0000008 -- Chromium's own
out-of-memory exception code -- in the arm where the heap was handed back while
the browser was starting, which is what a real desktop's heap does all day. That
the code varies with the exact heap state is itself measured here, so a third
code in the wild is consistent with this diagnosis rather than evidence against
it. It is not a demonstration, and it is written down as an unexplained gap in
the sentence that reports it rather than in a caveat at the end. Eighty launches
produced no 1.

ONE THING THE REPRODUCTION FOUND BY ACCIDENT. A CreateWindowExW refused for want
of desktop heap does not reliably set a last error: filling with 2,048-character
titles it reported GetLastError = 0, on a 512 KB heap and on the 20,480 KB one
alike, while filling with one-character titles it reported
ERROR_NOT_ENOUGH_MEMORY and filling with 23,718 small windows reported
ERROR_NO_MORE_USER_HANDLES. Three answers to one shortage, and the least
informative is the one the failing regime gives -- which matters because
WindowImpl::Init in Chromium's ui/gfx/win/window_impl.cc crashes on exactly the
no-error branch, through NOTREACHED(), and a check does not log. That
attribution is marked INFERRED where it is written: it joins a measured last
error to a source branch read the same day, and nothing here read a stack.

WHAT LANDED WHERE. QUESTIONS.md section 8 is amended BY ADDITION -- the entry's
existing text, including the sentence the experiment falsified, is left standing
and the new block sits under it, and the recommendation is replaced with five
directions and a recommendation of (b), make the failure name itself. The
measurement is in kb/windows/processes.md beside the saturation entry it
answers, with a re-establishment procedure written to stand WITHOUT the rig,
because the rig is in .work/ and this machine deletes that. The saturation
entry's own sentence -- "desktop heap, which no documented API reports" -- is
corrected in place with the previous wording quoted: UOI_HEAPSIZE reports the
SIZE and it is the USAGE nothing reports.

ONE COUNT MOVES, AND IT IS THE HAZARD TALLY. One row arrives open carrying
evidence and nothing crosses, so rows that are open while carrying evidence
rises 42 to 43 and closed stays at 146. The predicate is quoted rather than
paraphrased and the previous sentence is quoted inside the correction clause.
The row's subject is the failure mode itself -- a browser that cannot create a
window dies without saying so, and no API reports the resource that ran out --
and it is open because nothing in the product detects or names it. What would
close it is a decision that has not been taken.

THE GATE, AND A RESIDUAL CLOSED WITH IT. One full run from PowerShell and one
from Git Bash, detached, teed, polled by filename, never overlapping: 640 of 640
in both, filter FULL RUN in both, and the two halves received different drive
letter spellings this time -- upper from one and lower from the other -- so the
gate really was two instruments. The PowerShell half reports first-run bytes
CDN, downloading 203.8 MB because the cached tree was 84 minutes old: that is
the first genuine CDN handshake under Node v24.20.0 and its NSS 3.125 roots,
which had never fetched, and it succeeded. The Git Bash half reports CACHED from
the tree the first half had just published, which is the expected reading and
not a gap. Neither run produced the silent death.
