# Codex project registrations that resolve on any PC -- findings, 2026-10-10

Everything below was read or measured on 2026-10-10 on this machine (Windows 11 Pro 10.0.26300), between 12:59Z (first Codex call) and 14:03Z (last check that nothing was left running). Every Codex and Claude Code call ran with `CODEX_HOME` and `CLAUDE_CONFIG_DIR` in this folder. No BrowserAI, browser or installer was started. The probes are a stub named `BrowserAI.exe`.

## 1. The answer in brief

- **Codex still expands nothing in an MCP server's `command`.** The newest Codex on this machine is codex-cli 0.162.0-alpha.2. With `${LOCALAPPDATA}`, `$LOCALAPPDATA`, `%LOCALAPPDATA%` and `~` (each with `/` and `\`), at project and user scope, three rounds: **0 of 48 started**. Each failed with *"MCP startup failed: The system cannot find the path specified. (os error 3)"*. The 0.159.0-alpha.12.1 build gave 0 of 8.
  - The launch chain is byte-identical in the newest release (`rust-v0.162.1`), the newest prerelease (`rust-v0.163.0-alpha.5`) and the measured build. Nothing on it expands a variable or `~` in `command`, `args`, `env` or `cwd`.
  - openai/codex#2680 is open, with no linked pull request.
- **A project entry is read only in a trusted project, but the app-server can trust one by itself.**
  - No trust entry and a read-only sandbox: 0 of 12 project entries loaded. `trust_level = "untrusted"`: 0 of 12.
  - A `thread/start` whose effective permissions can write the folder writes `trust_level = "trusted"` for the folder's git root into the user's `config.toml`. This was measured with full access (3 of 3, and then 12 of 12 entries loaded). Source says workspace-write does the same once the Windows sandbox is set up; that was not measured.
- **Four forms resolve without a variable in `command`, and each fails differently:**
  - **A, the bare name `BrowserAI.exe` on Codex's own PATH (today's entry).** It fails for any Codex process started before the install: 0 of 6, *"program not found"*. It also starts whichever `BrowserAI.exe` comes first on PATH: 3 of 3 started the other copy.
  - **B, the same bare name with the entry's own `env.PATH = '~\AppData\Local\BrowserAI.app\current'`.** It started 33 of 33 with a clean argument list in every condition measured: Codex started before the install, another copy earlier on PATH, and spaces and `& ! ^ % ( )` in the profile path. When that entry finds nothing, Rust's own process search falls back to Codex's PATH: 3 of 3 started that way, 0 of 3 when that PATH lacked the install too.
  - **C, `cmd.exe /d /v:on /c !LOCALAPPDATA!\...`.** It started 27 of 27, but **hands the server a split argument list whenever the profile path contains a space** (6 of 6).
  - **D, a committed `.codex/browserai.cmd` named relatively.** It only works for a thread opened at the project root: 0 of 3 in a subfolder when the app-server runs outside the project, which is how the desktop app runs it.
- **No form opens a window.** Codex starts every stdio server with `CREATE_NO_WINDOW`. In 48 sessions and 96 process-tree censuses, no process of any app-server tree owned a top-level window. The window probe's positive control does find a window that is never shown.
- **Recommendation: B, keeping the installer's user-PATH entry.** It is the only form measured to resolve in every condition, and when it fails it behaves like today's form.
- Claude Code 2.1.296 still expands `${LOCALAPPDATA}` in a project `.mcp.json` `command`: 6 of 6 connected, including a space in the expanded path.

**What a program name resolves against:**
- MCP launches use the thread's local environment folder, or a host fallback (`core/src/session/mcp.rs:163-180`).
- `which` 8.0.0, `finder.rs`:
  - A name containing a separator is joined to the working directory (79-94, 123-138).
  - A bare name is searched in PATH entries only.
  - **Each PATH entry goes through `tilde_expansion`** (151-154, 242-262). The home folder comes from `env_home`, which reads `USERPROFILE` (`sys.rs:145-155`; `env_home` `lib.rs:47-55`).
- Rust std 1.95.0, `library/std/src/sys/process/windows.rs`, `resolve_exe` (464-522) and `search_paths` (526-583):
  - A path with a separator is not searched.
  - A bare name is searched in this order: the child's PATH, codex.exe's own folder, System32, the Windows folder, and **last the parent's (Codex's own) PATH**.
  - If nothing matches, the error is *"program not found"* (521).

**Windows process creation:** `child_command.rs:94-126` sets `env_clear`, piped stdio and `CREATE_NO_WINDOW` (104-105). `win/job.rs:125-133` adds `CREATE_SUSPENDED` (used at `stdio_server_launcher.rs:297-307`), and the process is assigned to a job object (325-344). Without a job object, Codex's terminator only holds the process it started (345-357).

**Trust:**
- `loader/mod.rs:1653-1757`: every `.codex/` folder from the project root down to the thread's folder is a layer, and an untrusted layer is loaded disabled. The trust decision is at 1047-1091 and its message at 1093-1111. The keys a project file may not set (89-102) do not include `mcp_servers`.
- **`app-server/src/request_processors/thread_processor.rs:1350-1377`**: when `thread/start` names a folder with no trust decision, the app-server may trust it. It does so if the effective permission profile is `Disabled` or `External`, or a managed profile that can write the folder. It then writes `trust_level = "trusted"` for the git root (or the folder) into the user's `config.toml`.

- `config/src/config_toml.rs:821-833`: on Windows, if the Windows sandbox is not set up, a requested workspace-write becomes read-only.
- The terminal client asks *"Trust this folder? ... Your trust decision will be saved."* (`tui/src/onboarding/trust_directory.rs:70-73`), and that trust applies to the repository root (147).

## 6. Measurements

**The rig.** `rig/` drives `codex app-server --listen stdio://`:
- Each run gets its own scratch `CODEX_HOME`, and the model provider points at `127.0.0.1:9`. No turn is started, so no model is ever asked anything.
- Every configured server is `stub/ProbeStub.cs`. It records its image, command line, argv, folder, parent pid and console state, and answers the tool `probe_whoami`.
- Each session:
  1. sends `initialize` and `thread/start`, and waits for each server's startup status;
  2. takes a process-tree census and a window census;
  3. calls `mcpServerStatus/list` with and without the thread;
  4. calls `probe_whoami` on every ready server;
  5. closes stdin and ends anything left in its own tree, by pid.
- Rounds: `matrix.sh`, `matrix2.sh` and `matrix4.sh` ran 3 rounds against 0.162.0-alpha.2. `matrix3.sh` ran 1 round against 0.159.0-alpha.12.1. `summarize.js` writes the summaries.

**What changed from the 2026-09-24 rig, and why:**
- **Scratch `LOCALAPPDATA` and `USERPROFILE`** (`profiles\user`, `profiles\Jo Smith`, `profiles\Jo Smith & Co (!x^ 100%)`, `profiles\user-before`, each with `AppData\Local`). This keeps every write inside `.work`, and lets me put a space or special characters in the expanded path. The old rig wrote its probe under the real `%LOCALAPPDATA%`.
- **The probe is named `BrowserAI.exe`**, sits at `<LOCALAPPDATA>\BrowserAI.app\current\`, and is built as a **Windows-subsystem** binary, like the real one (origin/master `db50964e` declares `WinExe`; the installed file's PE subsystem is 2). A console-subsystem build in `BrowserAI.app\console\` is the control.
- **The PATH handed to Codex** is this process's PATH minus any entry holding a BrowserAI binary (none did), plus scratch entries per kind.
- **Entries are written directly into `.codex/config.toml`**, and every entry's `args` end with `--tag <name>`.
- **`sandbox_mode = "danger-full-access"`** (the old rig used read-only), so that no sandbox setup can run. **This turned on the app-server's auto-trust**, which the trust kinds then separate out.
- **`[features] plugins = false`**. Otherwise every start clones github.com/openai/plugins (65 MB).
- **`GIT_TERMINAL_PROMPT=0` and `GCM_INTERACTIVE=never`** are in Codex's environment, because Codex runs git itself.
- **Processes are observed** through one read of the process table, reduced to the app-server's pid tree or the probes' scratch paths, never by image name. Windows are counted with `rig/winprobe.exe`, keyed by owning pid. Its `--selftest` positive control found its own window that is never shown.

## 9. What it means for a committed project registration

**Every form is read only in a trusted project:** 0 of 24 entries loaded when untrusted (read-only or explicit). A full-access Codex app-server trusts the project by itself at the first thread. **A variable in `command` never works:** 0 of 56 across the two builds. An absolute path resolves on one machine only.

**A. The bare name on Codex's PATH (today's entry, Q294 b).** `command = 'BrowserAI.exe'`, `args = ['--mcp']`.
- **Works when** the install's `current\` folder was on that Codex process's PATH when the process started: 24 of 24, clean argv, any profile path, any folder.
- **Fails for any Codex started before the install:** 0 of 6, *"program not found"*. That lasts until the desktop app is restarted (it takes its environment at launch and never re-reads the registry). For the terminal CLI it may last until the daemon is restarted (read, not measured).
- **Silently starts another `BrowserAI.exe`** if one comes earlier on PATH (3 of 3).
- Fails if the installer's PATH edit is missing (not measured).
- No window.

**B. The bare name with the entry's own PATH, built from the home folder.**

```toml
[mcp_servers.browserai]
command = 'BrowserAI.exe'
args = ['--mcp']
env = { PATH = '~\AppData\Local\BrowserAI.app\current' }
```

- **Works whenever `%USERPROFILE%\AppData\Local\BrowserAI.app\current\BrowserAI.exe` exists when the server starts**, regardless of Codex's own PATH or when Codex started: 33 of 33 with clean argv. That includes Codex started before the install (6 of 6), another copy on PATH (3 of 3 started the install's copy), and spaces and `& ! ^ % ( )` (6 of 6).
- **If that entry finds nothing, it degrades into A:** Rust's search ends in Codex's PATH (3 of 3; 0 of 3 when that PATH lacks the install too). Keeping the installer's PATH entry therefore keeps today's behaviour as the fallback.
- **Fails** if LocalAppData has been moved out of the profile (not measured; the A fallback still applies), and in an untrusted project.
- **Costs:**
  - The server's PATH is exactly the literal entry `~\AppData\Local\BrowserAI.app\current` (that is what the probe saw). `BrowserAI.exe --mcp` must therefore not rely on PATH; source suggests it does not.
  - It relies on `which` expanding `~` in a PATH entry, which Codex neither documents nor tests. That held at 0.155.0-alpha.9.2, 0.159.0-alpha.12.1 and 0.162.0-alpha.2, all on `which` 8.0.0.
  - The ownership checks in RegisterAI and BrowserAI must recognise an entry with this `env` table as BrowserAI's.
- No window.

**C. `cmd.exe /d /v:on /c !LOCALAPPDATA!\BrowserAI.app\current\BrowserAI.exe --mcp`.**
- **Works** whenever `LOCALAPPDATA` is set (it always is; `shell_environment.rs:192`) and the install exists: 27 of 27. It does not depend on PATH or on when Codex started (3 of 3 before the install).
- **Corrupts the argument list** when the profile path has a space: 6 of 6 started with the path's tail as leading arguments, because cmd passes the expanded path to the child unquoted. Today's BrowserAI.exe would still find `--mcp`, but nothing guarantees it stays that way. A Codex entry cannot add quoting, because Rust escapes an embedded quote as `\"` (0 of 9 on 2026-09-24).
- **Adds a cmd.exe and a conhost.exe** beside each of the three server copies per session. cmd waits for its child (114 of 114), and the job object covers both processes.
- No window.
- **Never write the plain `%LOCALAPPDATA%` form:** 0 of 6 with a space, and an `&` in the profile path runs a second command.

**D. A committed `.codex/browserai.cmd` named relatively.**
- **Works only for a thread opened at the project root:** 15 of 15, clean argv.
- **Fails for a thread in a subfolder** when the app-server runs outside the project, which is the desktop app's case: 0 of 3, plus 0 of 1 at 0.159.
- It is a second committed file, and an executable one.

**The forms side by side:**

| Condition | A | B | C | D |
|---|---|---|---|---|
| Codex started after the install | 24/24 | 33/33 | 27/27 | 15/15 at root |
| Codex started before the install | **0/6** | 6/6 | 3/3 | 3/3 |
| Another `BrowserAI.exe` earlier on PATH | **starts it, 3/3** | install, 3/3 | install, 3/3 | not run (uses the expanded path) |
| Space or `& ! ^ % ( )` in the profile path | 6/6 clean | 6/6 clean | 6/6 started, **argv split** | 6/6 clean |
| Thread in a subfolder, app-server outside the project | 3/3 | 3/3 | 3/3 | **0/3** |
| Untrusted project | not read | not read | not read | not read |
| Console window | none | none | none | none |
| What the server receives | its usual PATH | PATH = one literal `~` entry | argv split on a space | its usual PATH |

**Recommendation: B, keeping the installer's PATH entry.**
1. It is the only form that resolved in every condition the maintainer's decision covers, 33 of 33, with the argument list intact.
2. When it fails, it falls back to A, so it is at least as good as today's entry in every case measured.
3. C corrupts the arguments for every profile path with a space.
4. D breaks for threads opened in subfolders in the desktop app.
5. A remains the fallback choice if replacing the server's PATH is unacceptable. Its failures are either visible (*"program not found"*) or silent (the wrong copy starts).

**What B would require:**
- RegisterAI's writer and the ownership check must handle the `env` table.
- `resolvesTo` should report what the tilde entry finds.
- `CodexProjectNote` needs new wording.
- `BrowserAI.exe --mcp` must not depend on PATH.
- kb row 161's re-establish step should require `tildepath` to start, and should check `cmdwrap_v`'s argument list.

Claude Code's entry stays `${LOCALAPPDATA}/BrowserAI.app/current/BrowserAI.exe`.
