## How 1.2.161 does the swap

All paths are under `src/bins/src/` unless named otherwise.

1. **Two temporary folders.** The new version and the backup of the old one are both random folders under `packages\VelopackTemp\tmp_*` (`commands/apply_windows_impl.rs:129-131`, `lib-rust/src/locator.rs:206-213`).
2. **Before the swap.** The new version is extracted (`:138-147`), the old version's obsolete hook runs (`:151-156`), and every process under the install root is stopped (`:158-159`).
3. **First rename** (`current\` to the backup folder): 11 attempts, 1 s apart (`:160-163`, retry helper at `shared/util_common.rs:36-52`). If it fails, `current\` is untouched. This is what was measured on 2026-10-08.
4. **Second rename** (new folder to `current\`): 31 attempts, about 30 s (`:172-177`). The comment at `:173` promises a rollback, but `:177` just returns the error. The rollback it meant is the commented-out robocopy at `:187-205`, which copied the backup back at `:190`.
5. **Cleanup.** After the step fails, both temporary folders are deleted unconditionally, including the backup, which is the old `current\` (`:275-278`).
6. **What gets logged.** With a restart requested, `commands/apply.rs:57-61` tries to start the old program. That fails at `shared/util_windows.rs:108-110` with "Unable to find executable to start", and the early return means the "Error applying package" line at `:61` never runs.
   - BrowserAI's background update path uses `restart: true` (`VelopackUpdateClient.cs:193`, `:213`).
   - So, by reading, its log shows 30 "Retrying operation" warnings and ends with "Apply error: Unable to find executable to start".
   - The "broken state" message is only logged on the `restart: false` path.
   - In every case Update.exe exits 1 and shows no dialog (`update.rs:135`, `:141-144`).
7. **Afterwards nothing can repair or remove it.**
   - `Update.exe apply` and `Update.exe --uninstall` both need `current\sq.version` (`update.rs:277`, `:311`; `locator.rs:120-125`).
   - Windows' Uninstall button runs exactly that `--uninstall` (`windows/registry.rs:32`, `:52`).
   - `Update.exe start` fails at `commands/start_windows_impl.rs:114-117`.
   - `Setup.exe` repairs it: `--silent` skips the dialog (`l18n/src/dialogs.rs:194-196`), and the installer itself rolls back on failure (`commands/install.rs:94-119`, `:150-165`).
   - BrowserAI's data lives in `%LOCALAPPDATA%\BrowserAI`, outside the install root, so a repair keeps it.
8. **macOS does it right.** At the same tag, `commands/apply_osx_impl.rs:43-47` restores the old bundle on this exact failure, tested at `:171-184`.
9. **The docs say otherwise.** Velopack's own docs (`docs/packaging/operating-systems/windows.mdx:38-42`, main @ `1ca8eea6`) promise a lock dialog, an error message and the old version launched. The lock-dialog code was removed by PR #392 and commit `bfe2b5cc` (2026-02-27).

**What triggers it:** something holding a file open inside the freshly extracted folder for more than about 30 s, realistically antivirus, EDR, backup or indexing software. Nothing of BrowserAI's own touches that folder. How often it happens is unknown.

## Is there a newer release?

No. Velopack and vpk on NuGet are both at 1.2.161 (published 2026-09-29), even with pre-releases included. 1.2.161 is GitHub's latest release and newest tag. The `develop` branch is identical to the tag. None of the open PRs that touch the Rust updater (#1079, #1073, #1066, #480) changes the swap.

## Does upstream acknowledge it as a defect?

Only in the code. The error text says "the app was left in a broken state". The rollback comment is a leftover. The macOS fix addresses exactly this. No issue tracks the Windows case, and the maintainer's 2026 stance on rename failures caused by antivirus is "not an issue with Velopack" (#897). The case is still strong, because the defect here is Velopack's own cleanup deleting its only backup, which its macOS code already guards against.

## Corrections for the HAZARDS row (read, not measured)

- On BrowserAI's restart path the log ends "Unable to find executable to start", not "broken state".
- Uninstalling from Windows Settings also fails in that state, and `Setup.exe --silent` repairs it while keeping the data.
- Even when the second rename succeeds on a retry, `current\` can be missing for up to about 30 s. Any relay or task start in that window fails.
