### Measured facts

**1. Raising the toast from NativeAOT**

- CsWinRT counts as generated code. The rule is `DECISIONS.md:694`. Microsoft Learn says setting the Windows TFM "adds references to the Windows SDK projection and runtime assemblies generated by C#/WinRT", and that `cswinrt.exe` turns WinMD files into C# that is compiled into an interop assembly (https://learn.microsoft.com/windows/apps/develop/platform/csharp-winrt/). Either way it is generated from Windows metadata, which is the licence question the rule exists to leave alone. The rule's wording is broader than current practice: `src/` already ships generator output from our own declarations (91 `[LibraryImport]`, 158 `[LoggerMessage]`, 3 `[GeneratedRegex]`). Its test (`ForbiddenDependencyTests.NoProjectUnderSrcReferencesTheCodeGenerator`) looks only for `Microsoft.Windows.CsWin32`.

**2. What happens on a click** (timings in `MEASUREMENTS.txt`)

- (a) Protocol activation. The launched URI is the button's `arguments` text exactly (`browserai-q254test:snooze`). The dropdown value is lost. The app launched 118 ms after the click. Registration is `HKCU\Software\Classes\<scheme>`.
- (b) COM activator. COM launched `"<exe>" -ToastActivated -Embedding`; COM appends `-Embedding` itself. `Activate` received the dropdown value, for example `[snooze='10m']`. `invokedArgs` is the button's arguments, or the toast's `launch` value on a body click (the dropdown value is sent then too). Click to launch took 21 to 40 ms. It works through `HKCU\Software\Classes\AppUserModelId\<id>\CustomActivator = {CLSID}` beside a shortcut that has no activator property, so Velopack's shortcut can be left alone. It also works with a registry-only app id (display name, icon path, activator); the result is `shots\registry-only-aumid-toast.png`. The second key is `HKCU\Software\Classes\CLSID\{clsid}\LocalServer32 = "<root>\current\BrowserAI.exe" -ToastActivated`.
- (c) In-process events only, no COM server. While the process that raised the toast is alive, its `Activated` event gets the arguments and `{snooze='reboot'}` 20 ms after the click. Once that process has exited, a click on a foreground or background button launches nothing, and the toast is consumed: the choice is lost. With (b) registered and the raiser listening, both handlers fire, 4 ms apart.
- Documentation: `activationType="background"` "is ignored for desktop apps" (Windows App SDK quickstart).
- Who writes the keys: the install and update hooks, `VelopackStartup.cs:122-124`, which run in `BrowserAI.exe`.
- What a clean uninstall must remove: the CLSID key and the `AppUserModelId\velopack.BrowserAI.app` key; pending toasts (`History.Clear(id)`) and scheduled ones (`RemoveFromSchedule`); optionally `HKCU\...\Notifications\Settings\velopack.BrowserAI.app`, which Windows creates at the first toast (measured). Velopack 1.2.158's `src/bins/src/commands/uninstall.rs` removes none of these.

**3. Dismissal**

- The X's accessible name is "Move this notification to Notification Centre".
- A raiser that is alive gets `Dismissed(UserCanceled)` 7 ms after the X, and the toast stays in the Notification Centre history, so it can still be clicked later. That later click was not measured; the COM documentation says the activator handles clicks from there too.
- A COM activator never hears the X: its interface has only `Activate` (`NotificationActivationCallback.idl:24-31`).
- A toast with its popup suppressed reports `Dismissed(TimedOut)` within 16 to 32 ms.
- A reminder toast stayed on screen for minutes after its raiser had exited.
- So the X can only be seen by a process that is still alive. The 6-hour default has to be recorded when the toast is raised, and an explicit choice overwrites it.

**4. Who raises it, and how a snooze is stored**

- Where the decision is made: "staged but not alone" is decided in `UpdateService.cs:345` (one census read) and `:348-361`. The pass runs once per server start and has no timer (`:260-295`, `DECISIONS.md:690`). The configuration app joins the census while its window is open (`src/BrowserAI.App/Program.cs:221-230`).
- A process-free re-ask is possible: a `ScheduledToastNotification` created by a process that exited at once was delivered by Windows at its due time into the Notification Centre, with no scratch process alive (entry `sch1`).
- Reading the boot time: current time minus `GetTickCount64` gave 07:13:44.23Z, with 18 ms spread over 100,000 reads. WMI agrees within 278 ms but takes 551 ms. `GetTickCount64` includes sleep and hibernation. In .NET 11, `Environment.TickCount64` switches to `QueryUnbiasedInterruptTime`, which excludes sleep (Learn breaking-change page). So the product must call `GetTickCount64` directly, or after .NET 11 a sleep would look like a reboot. Fast Startup: "Shut down" hibernates the kernel and does not reset the boot time; only Restart does. Fast Startup is off on this machine. The session logon time (`WTSQuerySessionInformation`) reads in 5 ms and moves on Restart, on a Fast-Startup power-on, and on sign-in. Results in `boot\results.txt`.
- How each choice persists: 10 minutes and 6 hours as a "not before" timestamp; after the next reboot as the boot or logon time at the moment of choosing; not for this version as the staged version string.

**5. What the sessions page can read from the live markers**

The marker is opened create-new, read-write, share-read (`LiveInstances.cs:314`). All ten markers in the real install's `live\` folder are 0 bytes today. Results in `share\results.txt`:

- Readers must allow writers. `File.ReadAllText` fails with a sharing violation (0x80070020). Opening for read with share `ReadWrite` or `ReadWrite|Delete` works and parses.
- Held-or-free can be tested without write access: a read open that shares only read also fails while the file is held.
- Readers must also allow delete. With `ReadWrite|Delete`, a reader never changes the census: a held marker stays held, and after the holder dies the reclaim still deletes it. Without the delete flag, the reclaim's delete fails. These are `LockFile.Read`'s flags.
- Torn reads happen. Rewriting one 4096-byte block in place in a tight loop tore 5 of 20,000 reads. Truncate-then-write gave 915 empty reads and 4 torn ones. So the record needs a checksum and a reader retry, and the file must never be truncated.
- Timestamps: a rewrite shows up in `GetFileAttributesEx` and by handle, but the directory listing showed a value 1.5 s stale while the file was open.
- A replace-by-rename sidecar fails with 0x80070005 while any reader has it open, even with the delete flag.
- What a server can publish: identity (pid, creation time, image path, version, kind: server or app); the client's name, title and version from `initialize` (`BrowserProxy.cs:492`; Codex is `codex-mcp-client`); activity (start time, last call time, calls in flight); its sessions from `SessionManager._live` (`SessionManager.cs:291`): directory, purpose, and whether a browser is open.

**6. Closing a server**

- (a) TerminateProcess on a verified pid. The charter allows it when pid, creation time and image path are verified on the same handle (`CLAUDE.md:17`, `build/BannedSymbols.txt:17-19`). `StrayCandidate.TryTerminate` already does this (`src/BrowserAI/Interop/BrowserProcesses.cs:580-598`), but it lives in the server project, not Core. Effects: the job objects take the node child and the browsers down unflushed, and a killed browser loses the persistent cookie (Chromium) and localStorage (`kb/playwright/provisioning-and-timings.md:1086-1090`); the session locks are left released and resumable; the instance directory is left for the next sweep; the end of the log is lost.
- (b) A named event per server. Prototype in `stopevent\`, NativeAOT, 6 of 6 runs; results in `stopevent\results.txt`. `Local\` and `Global\` names both create without elevation. Signal to callback took 0.17 to 0.23 ms; signal to exit took 60 to 66 ms, with a 50 ms stand-in for the disposals. Exit code 0. After exit the name cannot be opened, so a late signal reaches nothing. Wired to `stopping.Cancel`, it is the update lane's own shutdown path (`Program.cs:258`, `:454-455`, `:466-471`): the child's stdin closes and `@playwright/mcp` closes its browsers gracefully (`ChildProcessSession.cs:228-234`), so only sessionStorage is lost (kb `:1005-1006`); the instance directory is deleted and the log flushed.
- (c) A stop file the server polls. It needs a second timer, and the charter says exactly one exists (`BrowserIdleTimer.cs:9-10`, `DECISIONS.md:697`), or else a directory watch. Latency is the poll interval.
- What the client sees, all three cases: Claude Code re-dials on its next tool call, 3 of 3 (`DECISIONS.md:799`), and meets the one Q261 refusal on that connection (`:800`). Codex loses MCP for that thread until a reload or a new thread (`DECISIONS.md:799`, `HAZARDS.md:321`).

**7. Recency**

`BrowserIdleTimer.DefaultIdlePeriod` is 10 minutes, reset by every call, and the timer tracks calls in flight (`BrowserIdleTimer.cs:99`, `:166-176`). Inside that window the session's browser may still be open. The number should come from that constant; the timestamps come from what the server publishes.

### Implementation outline and the tests it needs

Build steps:
1. Core interop (`BrowserAI.Core/Notifications/`): WinRT helpers for strings, activation and interface queries; `ToastPlatform` (show, replace, update, remove, read history, schedule, cancel schedule, with SuppressPopup as a seam); `ToastActivator` (the class factory and `INotificationActivationCallback`); IIDs and slot numbers as named constants, each citing the SDK line.
2. `UpdatePrompt`, pure: the XML is the v3 shape with the default at `6h`; the decision takes the stamp, the time now, the logon time and the staged version; the stamp file lives in the data root, written temp-then-rename under a `Global\BrowserAI-UpdatePrompt-` mutex that never waits.
3. Registration: install and update hooks write the two keys; the uninstall hook removes them and clears pending and scheduled toasts.
4. Server: the `StagedButNotAlone` branch calls `UpdatePrompt.MaybeRaise`, with no event handlers.
5. Live markers: `LiveInstances.Join` writes the identity record; `Publish` rewrites it in place, throttled, with a length and a checksum; `ReadAll` reads with `ReadWrite|Delete` sharing and retries a torn read; the stop event is created at join, and its wait calls `stopping.Cancel`.
6. Configuration app: a `-ToastActivated` COM-server mode (a snooze writes the stamp, schedules the next toast and exits; Review opens the window at the sessions page); `SessionsPage.Page(servers, now)` as a pure function; closing sends the stop events and then, per question 9(a), does a census-checked apply; `--report` gains the list of servers.
