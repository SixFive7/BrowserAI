Title: Windows x64: StackSamplingProfiler crashes the browser when a sample lands on vzeroupper between pop rbp and ret

Chrome for Testing 157.0.8101.0, 156.0.8078.4 and 155.0.8059.12, win64
Windows 11 Pro 26H2, build 26300.9550, x64, AMD Ryzen 9 5950X
Windhawk 1.7.3 is installed. windhawk.dll is loaded in the browser process with and without the flag and is not on the crashing stack.

## Steps

1. `npm i playwright@1.64.0`
2. `npx playwright install chromium`
3. `node repro.mjs`

The script launches Chrome for Testing headless 20 times, alternating plain launches with launches given `--disable-stack-profiler`, and after each launch takes full-page PNG screenshots of a 1920x16384 page for 28 s.

```js
// repro.mjs
import { chromium } from 'playwright';
import fs from 'node:fs';
import os from 'node:os';
import path from 'node:path';

const url = 'data:text/html,<style>html,body{margin:0}</style><div style="height:16384px;background:rgb(48,96,192)"></div>';
const tally = { on: { launches: 0, lost: 0, captures: 0 }, off: { launches: 0, lost: 0, captures: 0 } };

for (let i = 0; i < 20; i++) {
  const arm = i % 2 === 0 ? 'on' : 'off';
  const profile = fs.mkdtempSync(path.join(os.tmpdir(), `profiler-${arm}-`));
  const context = await chromium.launchPersistentContext(profile, {
    channel: 'chromium',
    headless: true,
    viewport: { width: 1920, height: 1080 },
    args: arm === 'off' ? ['--disable-stack-profiler'] : [],
  });
  const page = context.pages()[0];
  const started = Date.now();
  tally[arm].launches++;
  try {
    while (Date.now() - started < 28000) {
      await page.goto(url);
      await page.screenshot({ fullPage: true });
      tally[arm].captures++;
    }
  } catch (error) {
    tally[arm].lost++;
    console.log(`launch ${i} (${arm}): lost at ${Date.now() - started} ms, ${error.message.split('\n')[0]}`);
    console.log(`  dumps: ${path.join(profile, 'Crashpad', 'reports')}`);
  }
  await context.close().catch(() => {});
}
console.log(JSON.stringify(tally));
```

## Analysis

1. An x64 epilog may hold only `add rsp` or `lea rsp`, then pops, then `ret` or `jmp`: "No other code can appear." (https://learn.microsoft.com/en-us/cpp/build/prolog-and-epilog). RtlVirtualUnwind finds an epilog by reading the code at RIP. On `vzeroupper` it finds none, takes RIP for body code and reverses the whole prolog.
2. UWOP_SET_FPREG puts the frame base at RBP - 0x80. `pop rbp` has already run, so RBP holds the caller's value, 0 here. The frame base is -0x80 (r8), the saved xmm6 is read at -0x80 + 0x290 = 0x210 (r9), and the read of its upper half at 0x218 faults.
3. The 0x11d dump is the same in another function: RIP chrome.dll+0x54e4350 (155.0.8059.12), RBP 5, xmm6 at 0x190, so 5 - 0x80 + 0x190 = 0x115 and the fault is at 0x11d. The GPU bot stacks in 462642963 and 450325666 show 0xffffffffffffff81 among the RtlVirtualUnwind2 arguments, which is RBP 1 minus 0x80.
4. Each of the three builds holds 80 byte sequences 5d c5 f8 77 c3 (`pop rbp; vzeroupper; ret`) in chrome.dll .text, and 1,514 to 1,545 of `pop <reg>; vzeroupper; ret`.
5. The sampled thread is CrBrowserMain: in the 10 dumps from 155 and 156, a register of the sample points into CrBrowserMain's stack (RDI in 9, R13 and R14 in 1). In 157 RDI points into the stack copy instead (0x46bc006bae30, RSP 0x46bc006ba808). PageHandler::ScreenshotCaptured runs the PNG encoder on the UI thread: https://chromium.googlesource.com/chromium/src/+/refs/tags/155.0.8059.12/content/browser/devtools/protocol/page_handler.cc#1960
6. The copy is walked on a ThreadPool sequence, which puts the fault on ThreadPoolForegroundWorker: https://chromium.googlesource.com/chromium/src/+/refs/tags/155.0.8059.12/base/profiler/stack_sampler.cc#263. Win32UnwindFunctions::VirtualUnwind calls ::RtlVirtualUnwind directly: https://chromium.googlesource.com/chromium/src/+/refs/tags/155.0.8059.12/base/profiler/win32_stack_frame_unwinder.cc#62
7. https://chromium-review.googlesource.com/8482885 restores R12 to R15, RDI and RSI in the register rewrite. The frame register here is RBP, which was rewritten before that change, and 0 is not a stack address. 157.0.8101.0 contains the change and still lost the browser in 4 of 10 launches, every dump on +0x1d103bc.
8. Chrome for Testing runs the profiler on every launch. GetReleaseChannel() returns nullopt unless OFFICIAL_BUILD and GOOGLE_CHROME_BRANDING are both set (https://chromium.googlesource.com/chromium/src/+/refs/tags/155.0.8059.12/chrome/common/profiler/thread_profiler_configuration.cc#44), a Chrome for Testing build cannot be Chrome-branded (https://chromium.googlesource.com/chromium/src/+/refs/tags/155.0.8059.12/build/config/chrome_build.gni#80), and DefaultPlatformConfiguration::GetEnableRates() then enables the profiler for 100% of launches (https://chromium.googlesource.com/chromium/src/+/refs/tags/155.0.8059.12/chrome/common/profiler/thread_profiler_platform_configuration.cc#63). The startup profile samples every 100 ms for 30 s (https://chromium.googlesource.com/chromium/src/+/refs/tags/155.0.8059.12/chrome/common/profiler/thread_profiler_configuration.cc#69). chrome-headless-shell 155.0.8059.12 runs no StackSamplingProfiler thread.

## Ask

- Make the Windows unwinder survive this epilog shape. One way: when the bytes at RIP are c5 f8 77 c3 (`vzeroupper; ret`), the pops are done, so unwind it as a `ret` (RIP from [RSP], RSP + 8) without calling RtlVirtualUnwind.
- Or turn the profiler off in Chrome for Testing.

Minidumps of all three builds are available on request. They hold process memory, so none is attached.
