### Q226 — event id 76 was shared by two live events, and the repair moved one of them. Was that the right half to move?

**Primer.** `ProxyLogTests` (new today, for Q224 b) found on its first run that `ClientLivenessLog` declared **id 76 twice**: `ClientHasAlreadyExited` took it in `ec6d858` on 2026-09-15 and `ClientWaitCannotBeInterpreted` took the same id in `bf27512` one day later. Nobody had noticed. **Both are in `v1.0.0`**, so every shipped binary emits 76 for two different events and only the message text tells them apart. Unlike Q224's id 16 — where the old meaning shipped for two days and is in no fetchable artifact — here BOTH meanings are live in the field right now. Something had to move or the suite stays red on a rule the maintainer just asked for.

**Directions.** (a) **Move the LATER one**, `ClientWaitCannotBeInterpreted` 76 -> 77, so 76 keeps the meaning it had first. TAKEN as the reversible default. (b) Move the EARLIER one instead, on the argument that `ClientHasAlreadyExited` is the rarer event and disturbs fewer queries. (c) Move BOTH to fresh ids and retire 76 entirely, so no query written against a v1.0.0 log can be silently answered by a v1.1.0 one. (d) Renumber nothing and exempt this pair in the test, recording the ambiguity — rejected here, because it is the one shape that weakens a rule to fit the code.

**Recommendation: keep (a).** It matches the Q224 principle — the first meaning owns the id — and it is one line to change to (b) or (c) if he disagrees. (c) is the only option that makes a v1.0.0 log unambiguous, and it costs a second stale id.

### Q227 — 1.1.0 publishes a full package and NO delta, and this is the first release where a delta was possible.

**Primer.** The clean re-pack (`RELEASING.md`'s running order, step 5) empties `Releases/` so the feed holds only this release's rows. With nothing to delta against, `vpk` emits a full package alone: `releases.win.json` holds exactly one row, 55,022,728 b, which is the shape the published `v1.0.0` feed has. **For v1.0.0 that was unavoidable — it was the first release.** For 1.1.0 it means every existing install downloads ~55 MB where a delta would have been about **139 KB** (measured today, same-tree, at 138,791 b). The delta is the thing the charter says Velopack was chosen for. Nobody has ever applied an update from this feed, so nothing is broken today; what is at stake is the first real update.

**Directions.** (a) **Ship the full package alone, as the checklist produces it.** TAKEN as the reversible default, and it is what v1.0.0 did. (b) Stage the published `1.0.0` full package into `Releases/` before the re-pack so `vpk` emits a `1.0.0 -> 1.1.0` delta, and publish both rows. (c) Same as (b) but as a script change in `New-Release.ps1`, copying the previous release's full package out of `Releases/archive/` automatically, so no release forgets. (d) Decide deltas are not worth the feed complexity for a product with one install, and say so in DECISIONS so the charter's claim is narrowed rather than quietly unmet.

**Recommendation: (c), but not in this cut.** It is a behaviour change to the release script and belongs to whoever owns it; (b) by hand for this release would work and is exactly the kind of by-hand step `Clear-TestPackFeed.ps1` was written to remove.
