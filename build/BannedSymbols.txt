; NEVER BY IMAGE NAME -- the repository-wide half of the banned list, applied to
; every project by Directory.Build.props, product and test alike. The rule has
; no exception for test code: a harness that counts chrome.exe is a harness that
; will one day be adapted into a sweep that kills one.
;
; It is a STRUCTURAL rule and not a review item because a review already
; passed on code that violated it. The Chromium probes this project grew out of
; counted and killed by image name -- harmless for Chromium on that machine, and
; the same code adapted to Firefox would have killed ~40 of the maintainer's own
; firefox.exe processes.
;
; The invariant: BrowserAI can only terminate a process that belongs to a job
; object it created, or whose identity it verified against a path it owns. Two
; mechanisms, no third.
;
; What an analyzer cannot see -- `taskkill /IM`, a WMI query filtered on Name, a
; toolhelp walk that matches szExeFile -- is covered by NeverByImageNameTests,
; which reads the tree as text. The two together are the mechanism; neither on
; its own is.
;
; Corrected 2026-08-16: the sentence above was true of three of those four and
; NOT of the toolhelp one, for as long as it existed. The test's needle list
; carried taskkill, GetProcessesByName, Win32_Process and Get-Process and
; nothing for toolhelp, so this file asserted a coverage nobody had written --
; which is worse than an admitted gap, because it stops the next reader looking.
; Found by the plan's final audit; the needle is szExeFile, the one member a
; toolhelp walk can learn a name from.
;
; The product's own additional bans (Console, Debug) live beside it in
; src/BrowserAI/BannedSymbols.txt. Both files are named BannedSymbols.txt
; because that is the name the analyzer looks for, and it reads every one it is
; given.

; ADDED 2026-08-17. Two more rules, both repository-wide for the same reason the
; one above is: the violation each exists to prevent has already happened here,
; and one of the two happened in TEST code.

; NEVER Directory.Delete(recursive: true). Every tree delete goes through
; Runtime/TreeDelete.cs. This file is the EDIT-time half -- the message appears
; in the IDE before the edit is saved -- and it is the half that was missing:
; ScratchRoot's reclaim pass used the framework primitive until 2026-08-17 and
; was caught by a manual audit, which is not a mechanism. A ban scoped to src/
; would not have caught the only violation of this rule this repository has.
;
; It takes ZERO suppressions, and that is stated here because it is not what
; anyone expects. TreeDelete itself calls the SINGLE-argument overload -- the
; non-recursive one, post-order, at the last step of each level -- which is a
; different symbol and is not banned. Banning it would be wrong: it is the
; correct primitive inside a per-node walk. The suite's five call sites went to
; ScratchDirectory.RemoveTree, so there is no exception anywhere.
;
; CORRECTED 2026-08-18: this ban justified itself on REPORTING alone, and that
; was incomplete in the one direction that matters -- it named what the banned
; call does worse and nothing it does BETTER, so a reader comparing the two
; would have concluded the replacement was a superset. It was not. The framework
; call checks FILE_ATTRIBUTE_REPARSE_POINT while it walks and unlinks a junction
; instead of descending into it; TreeDelete.Remove did not, and on a
; caller-named path -- browserai_destroy takes the directory from the model --
; one junction inside a browser profile emptied the target. Fixed the same day
; and asserted by TreeDeleteTests with a real junction. The rule for whoever
; replaces this routine next: a replacement must keep BOTH properties, or the
; ban is protecting a downgrade.
;
; NEVER the timed Process.WaitForExit overload alone. It returns as soon as the
; process is gone and does NOT drain the asynchronous output readers, so stderr
; is silently truncated -- a green build that loses the line explaining a
; failure, which is this project's founding defect class. The parameterless
; overload is what flushes the event queue. No call site is left in src/ since
; 2026-10-03, when Registration/ClientCommandLine.cs went to RegisterAI with the
; rest of the registration code (previously "There is exactly one legitimate call
; site, Registration/ClientCommandLine.cs"). A new one carries an RS0030
; suppression with the reason beside it AND a bare WaitForExit() on the next
; statement. The suppression permits the timed call and cannot require the flush,
; so the pairing has a test of its own:
; ProcessLogTests.EveryTimedWaitForExitIsFollowedByABareOne, added 2026-08-17,
; which fails if the second call is ever deleted. Without it, deleting that line
; leaves the suppression, its comment and the whole build intact.
;
; CORRECTED 2026-10-11 (previously the rule above was "NEVER the timed
; Process.WaitForExit overload alone", with a suppression and a bare
; WaitForExit() after it as the way to keep one): every overload is banned
; since the maintainer's decision 54, below. WaitForExitAsync waits for the
; process and then for the end of both event-driven readers, read in .NET
; 10.0.12's own System.Diagnostics.Process on 2026-10-11 and held by
; ProcessLogTests.WaitForExitAsyncWaitsForTheEndOfBothRedirectedReaders, so
; nothing a timed wait used to lose is lost, and a bound is a CancellationToken.
;
; NOT HERE: the Microsoft.Playwright package. A banned symbol is the wrong
; mechanism for a dependency -- with no PackageReference the type does not
; resolve, the analyzer matches nothing, and the entry reads as coverage while
; providing none until somebody has already added the package AND written code
; against it. The reference itself is the earlier and stronger signal, so it is
; asserted over Directory.Packages.props by
; ForbiddenDependencyTests.NoProjectDrivesPlaywrightDirectly.

M:System.Diagnostics.Process.Kill(System.Boolean);Never Process.Kill(entireProcessTree: true). It walks parent-child links, which are re-parentable and pid-reusable, and it loses the race against anything that respawns while it walks. Dispose the JobObject instead: KILL_ON_JOB_CLOSE tears the whole job down at once and contains anything spawned mid-teardown.
M:System.IO.Directory.Delete(System.String,System.Boolean);Never Directory.Delete(recursive: true). It reports ONE failed node where a tree may hold many, and a caller whose answer is 'what survived' then cannot give one. Use Runtime/TreeDelete.Remove, which walks post-order and names every node it could not remove. In the suite, ScratchDirectory.RemoveTree. The single-argument overload is not banned: it is the correct primitive inside that walk. NOTE what this call does BETTER, because until 2026-08-18 the replacement did not do it: it checks FILE_ATTRIBUTE_REPARSE_POINT during its walk and unlinks a junction or directory symlink instead of descending into it and deleting the target's files. TreeDelete.Remove checks it too now, and TreeDeleteTests proves it with a real junction. A future replacement must keep BOTH properties -- the per-node report and the reparse-point check -- or it is a downgrade wearing a house rule.

; ADDED 2026-10-11. NEVER BLOCK A WORKER -- the maintainer's decision 54, in his
; words verbatim: "54 Wow that is unexpected! I cannot fathom any good reason to
; ever use .GetAwaiter().GetResult() or Thread.Sleep() anywhere ever when we are
; building on the TPL or similar framework. Remove all such occurances and go
; fully async like a nice person. Never block a worker anywhere. Fix all
; occurances throughout the entire codebase. While scanning if you ever deem
; there to be any good reason for it in this goodbase I want to review your
; reasoning. Otherwise make it fully async."
;
; Why it is a rule and not a habit: the release gates of that day went red on a
; starved thread pool in the test host. A sync-over-async pipe read parked two
; pool threads per byte, retry loops slept on pool threads, and the pool injects
; a thread a second past its minimum for a blocked worker it cannot see waiting
; on a task. Every call below parks the thread that makes it until something
; else happens, so each is banned here, repository-wide, product and suite
; alike, and the build is red wherever one stands.
;
; FIVE PLACES KEEP A WAIT, ALL APPROVED, AND ONE KIND OF THREAD WAITS FOR ITS
; WORK. Corrected 2026-10-12 (previously "FIVE PLACES KEEP A WAIT, and four of
; them are approved", with SessionLockTests' four waits the fourth place and the
; relay's standard input and output measured before he decided). The maintainer's
; answers of that day, in his words verbatim: "78-82 your recommendation". 78 a
; approved the fifth: StdioChannel's read and its write and flush carry their
; suppression, with the measured reason that both clients hand a synchronous pipe
; end Windows refuses to reopen overlapped (231), switch in place or bind to a
; completion port (87). 79 c freed SessionLockTests' four: the destroy's delete
; is awaited outside the session's lock, and the two arms await. So the places
; are the mutex's owner thread, the log's sink, JobContainmentTests' read of an
; anonymous pipe and the relay's standard input and output; and
; Runtime/DedicatedThread's wait for its next item, the thread 78 b, 80 b, 81 c
; and 82 b run their synchronous calls on (the relay's output, the file system,
; each session store), carries one suppression of its own.
;
; The approval of 2026-10-11, 76 b, in his words verbatim: "76 b - but also, why is the session-delete path not async? Is it just the test that is sync or is there another path still not async?"
; Corrected 2026-10-11 (previously
; "SIX PLACES KEEP A WAIT, ten calls in all, and each is listed for his review
; and carries no suppression until he has read the reasoning, so the build
; stays red at every one until then"). The owner thread of a named kernel mutex
; (Sessions/MachineMutex.cs, two calls): a Win32 mutex belongs to the thread
; that took it and only that thread can release it, so a mutex held across an
; await needs a thread that takes it, parks until the hold ends and releases
; it, and that thread is the mutex's own, never a pool worker. The process
; log's sink (Logging/RollingFileWriter.cs): ILogger.Log is synchronous, and a
; record must be in the file before Log returns, so that a process that dies
; on the next line leaves the line that explains it. The relay's standard
; input and output (Protocol/StdioChannel.cs, a read and a write): the handles
; are the client's and none of them was opened for overlapped I/O, so each is
; read and written on a thread of its own. Corrected the same day (previously
; "TWO PLACES KEEP A WAIT", the mutex and the log), when the conversion reached
; the channel and the suite: the suite's read of an anonymous pipe
; (JobContainmentTests, whose subject is one, and an anonymous pipe has no
; overlapped read), and the four waits two arms of SessionLockTests make from
; inside the product's synchronous delete callback, which runs under its lock,
; to watch a second thread contend for it.
;
; NEVER READ OR WRITE A FILE SYNCHRONOUSLY -- the maintainer's decision 63, in
; his words verbatim: "convert disk writes as well. Some users have slow
; spinning rust." Reads are converted with the writes, for the same disks.
; Every call below is a synchronous read or write of a file or of a stream, so
; each is banned; File.ReadAllTextAsync, File.WriteAllBytesAsync and their kin,
; or a FileStream opened with FileOptions.Asynchronous and its async methods,
; are the replacements. A FileStream constructor that cannot open for
; asynchronous I/O is banned with them, and HouseRuleTests holds the ones that
; can to FileOptions.Asynchronous, which an analyzer cannot read off an
; argument.
;
; WHAT THIS LIST CANNOT SEE, stated so that it does not read as coverage: a
; call through a TextReader or TextWriter reference (Console's streams among
; them), a P/Invoke that waits (WaitForSingleObject, LockFileEx, ReadFile on a
; synchronous handle), SQLite's own file I/O, which is native and has no
; asynchronous form, and the file system's metadata calls (File.Exists,
; File.GetLastWriteTime), which Windows offers synchronously only. Corrected
; 2026-10-12 (previously "SQLite's own file I/O ... and the file system's metadata
; calls (File.Exists, a directory listing, File.Move)"): since 80 b and 81 c the
; product's listings, creations, deletions and renames are banned by
; src/BrowserAI/BannedSymbols.txt and made on Runtime/FileSystemThread, and since
; 82 b a session store's statements run on the store's own thread, which
; Storage/SessionStoreConnection checks at run time, as no list can. And an
; asynchronous read or write of a stream that was not opened for overlapped
; I/O, which the framework serves as a synchronous call on a pool thread: a
; System.Diagnostics.Process's redirected streams are such streams (kb,
; windows/processes.md, measured 2026-10-11). The product and the suite read
; their children through Interop/JobLauncher's overlapped pipes, the suite
; through Harness/ChildRunner, and the one Process whose redirected streams the
; suite still reads is ProcessLogTests' measurement of Process itself.
; Corrected 2026-10-11 (previously "and the suite still reads its own children
; through them, where the product reads its children through
; Interop/JobLauncher's overlapped pipes"), when the suite's runs moved.
