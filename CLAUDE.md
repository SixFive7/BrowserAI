# BrowserAI — working instructions

BrowserAI is a Windows-only, NativeAOT .NET MCP server that proxies a bundled `@playwright/mcp` child over stdio. **Tagged `v1.0.0`, and nothing has been distributed.** *Corrected 2026-08-24 (previously "**Shipped at `v1.0.0`.**")* — the annotated tag exists and is pushed, and no build has ever been handed to anyone. **This one was load-bearing**: several decisions were argued from *"`v1.0.0` shipped, so sessions exist in the wild"*, and there are no sessions in the wild. Nothing is enforcing this sentence; the tag is what `git tag --list` says and the distribution is what a person knows. [`README.md`](README.md) is what it is and how to use it; [`DECISIONS.md`](DECISIONS.md) is the charter and the still-open design questions; [`ARCHITECTURE.md`](ARCHITECTURE.md) maps each part of it to the code that satisfies it; [`HAZARDS.md`](HAZARDS.md) is the known failure modes, maintained by addition and never by removal; [`TESTING.md`](TESTING.md) is the suite and the release gate; [`RELEASING.md`](RELEASING.md) is the checklist; [`TODO.md`](TODO.md) is work settled in intent and not yet done. **Measured facts go in [`kb/`](kb/README.md)** — in the article they belong to, never a new top-level file, each with a date, the versions it held under, and how to re-establish it. **Never update a measurement by reasoning: re-run it, or mark the entry `[STALE]`.**

## Prefer a mechanism over a habit

**If a rule can be a failing test, a hook or an analyzer, make it one — and then say which one.** The SPDX rule was kept by 222 files out of 224, which is what a habit looks like right up to the moment somebody adds the 225th. So every rule below either names what enforces it or says plainly that nothing does, and the second list is the one that needs a reader rather than a build.

## Rules nothing enforces — these need a person

- **Update first, then work.** Re-resolving every dependency to latest is the *first* step of touching this project, not a step before release. Deferring it is how a project stops following the lead and starts accumulating one upgrade nobody ever takes.
- **Never assert a version or a "latest" claim from memory.** If it was not looked up this session, say plainly that it is unverified — a confident stale version is worse than an admitted gap. Package questions to the `nuget` MCP server, .NET and C# to `microsoft-learn`, the rest to `context7`, preferring a vendor's own server because `context7` is metered.
- **Stamp what you verify and what you correct.** `Verified <date> @ <version>` for a claim confirmed still true; `Corrected <date> @ <version> (previously "X")` for one that was not. **The `previously` clause is the load-bearing half** — it is what tells a reader who learned the old value that it was reviewed and replaced rather than lost, and what stops the same correction being made twice.
- **Quote the predicate before the number.** Not *"54 rows"* but *"54 rows that are `open` and carry `—`"*. A re-count of the hazard index measured a different predicate over the same table and broke a figure that was correct; the five-row gap read as staleness rather than as a different question, and the fix went in the wrong direction.
- **A search that returns zero needs a positive control.** A sweep for personal paths reported the tree clean and was wrong, because a pattern that matches nothing is indistinguishable from a genuine absence. Prove the search can find something before believing that it found nothing.
- **Never delete a document written to be consumed without first recording what implements it.** That is what made deleting the implementation plan safe on 2026-08-17: the measurements had gone to `kb/`, the reasoning to the doc comment above the code it explains, and the `Implemented by` column had become [`ARCHITECTURE.md`](ARCHITECTURE.md).
- **A suite run is started detached, teed to a log, and the log polled** — never streamed through the caller's pipe. A grandchild that inherits the stdout handle keeps the pipe open after the command has exited, so the caller never sees EOF and its declared timeout does not fire; and a run stopped part-way used to take its output with it. Both shells' invocations are in [Testing](TESTING.md#how-the-suite-is-run-detached-teed-and-the-log-polled), which owns them. **A shared wrapper script is the wrong simplification**: each half forces its own drive-letter spelling and declares it, and that difference is [half the reason both shells are run](TESTING.md#continuous-integration). *Corrected 2026-08-24 (previously "the drive letter the test host inherits comes from the shell that started it") — inheriting it made the property hold [run to run rather than by construction](TESTING.md#the-two-spellings-are-forced-and-the-run-says-which-one-it-got), and a gate that ran one instrument twice reported what two report.*
- **The suite gate has two levels, and applying the release one to ordinary work costs six runs where two would do.** For ordinary work — a change, a fix, a batch of edits — the gate is **one full run from PowerShell and one from Git Bash**. Both shells, always: [each half forces its own drive-letter spelling and declares what it forced](TESTING.md#continuous-integration), so one shell leaves the other spelling unrun. **Three runs from each shell is the RELEASE gate and nothing else** — [`RELEASING.md`](RELEASING.md#the-release-gate) is a six-step sequence taken before a release, and the rule above is *no **release** with a red test*. What the repetition buys is the flake that shows up once in three, which is how the probe-report race in [the hazard index](HAZARDS.md#hazard-index) was found; on an intermediate batch it buys nothing. *Written down 2026-08-24, after the release gate had been applied to every intermediate batch.*

- **A filtered run is a development convenience, never a verification.** Only a full run is evidence, and the reason is stronger than caution: `--treenode-filter` reads `|` as an OR **inside one path segment** and never between path patterns, so six class patterns joined with `|` select the **whole suite** in one arrangement and the **first class only** in another — both reporting a clean pass, and one of them doing so while two of the tests it claimed to cover were red. [Measured 2026-08-24](kb/toolchain.md#a-filtered-run-covers-less-than-it-asked-for-and-reports-success-anyway--measured-2026-08-24), with the correct syntax, the counts side by side and a re-establishment procedure. Quote the filter: `|` is a pipeline operator in both shells, so an unquoted one is cut before the test host ever sees it. **Nothing enforces the RULE and nothing can, which is why it stays in this list — but the run now states the PREMISE.** A filtered run is a *correct* run — every number it prints is true of what it ran — and what is false is the sentence written underneath it, which no test can read. Refusing filtered runs would forbid the iteration loop this rule exists to permit, and flagging them would fire on every legitimate use and be tuned out in a day, so nothing does either. *Corrected 2026-08-24 (previously “Nothing enforces this and nothing can, which is why it is in this list … The nearest thing to a mechanism here is the one that actually caught it — a published count re-scanned by `RecordedCountTests` — and that works by disagreeing about something else entirely”).* What is mechanised since 2026-08-24 is the premise: the coverage block carries a **`filter`** row on every run — `FULL RUN`, `FILTERED` with the filter quoted, `UNREAD`, or `DISAGREED` — read from MTP's own `ITestExecutionFilter` through TUnit's `GlobalContext.TestFilter` and never from the process command line, and **`BROWSERAI_RELEASE_RUN=1` fails a run whose state is `FILTERED` or `UNREAD`**, so no release may be cut from a filtered run and a run that cannot tell never says *not filtered*. *Corrected 2026-08-24 (previously “turns `FILTERED` and `UNREAD` into failing **tests**”)* — it **was** a test, `SuiteCoverageTests.ARunThatWasFilteredIsNeverARelease`, and a refusal a `--treenode-filter` can deselect is not a refusal: the variable plus a filter that missed that one method ran green. It is raised from the `[After(TestSession)]` hook that writes the coverage block, which no filter reaches — measured at TUnit 1.65.0: an exception out of a session hook exits **10** and reports *Test adapter test session failure*. The limit is stated in [Testing](TESTING.md#the-run-says-whether-it-was-filtered-and-a-release-may-not-be): a run that never starts a session is refused by nothing. `ICommandLineOptions` was the first choice and is unreachable from a test; both facts are in [the kb entry](kb/toolchain.md#a-filter-reaches-the-test-hosts-own-command-line-under-dotnet-test--measured-2026-08-24), and the states are in [Testing](TESTING.md#the-run-says-whether-it-was-filtered-and-a-release-may-not-be). The positive control is a real filtered child process, because every run of this suite is unfiltered and a reading that can only ever come back empty is indistinguishable from one that cannot read. What caught the original was a positive control on a published count disagreeing about something else entirely. *Written down 2026-08-24, after a six-class filtered run was reported as evidence about six classes.*

- **Parallel work gets its own git worktree — and a worktree does not isolate a suite run, because the machine-wide state is not in the repository.** The browsers root, the session index, the live markers and the process log are one set per **app root**, and [the stray sweep is machine-wide by design](ARCHITECTURE.md#locking-ownership-and-the-sweep) — it hunts browsers belonging to *any* session — so two suites sharing an app root sweep each other's browsers, race each other's index and interleave in one log. The app root moves with `BROWSERAI_ROOT`, which [must be under the user's profile or startup refuses it](src/BrowserAI/Hosting/InstallRootScope.cs).

  ⚠️ **Setting it does not isolate a run, and setting it anyway reddens the suite for reasons unrelated to the change under test.** `BrowserAiPaths` resolves through `new LocalAppDataPaths()` with no root argument, so the harness goes on asserting against the default root while every product process the run starts inherits the override — around thirty assertions compare a launched browser's image path against the default one, and the empty new root also provokes a ~767 MiB provisioning download. Established 2026-08-24, independently, by two agents, and the resolution was then **considered and deliberately kept**: the assertions that read those members are about the real provisioned tree the empty root is standing in for, so honouring the override there would re-point them at the rig it was set up to create. `BrowserAiPaths.Real` is the one seam that would carry the change if it is ever wanted — one argument in one place rather than seven. **So parallel suite runs share one app root and are serialised by whoever is running them**, and a red of the shape *a browser vanished*, *a session's process is gone* or *an artifact directory was swept* may belong to the other run rather than to the change.
- **Newest stable idioms the GA toolchain compiles.** Familiar-but-dated patterns are style defects. `.editorconfig` catches the mechanical half and nothing catches the rest.
- **Every behaviour change gets a test that fails without it, planted and watched red before the fix goes in.** Nothing can enforce this and nothing ever will: a suite can see that a test exists, never that anybody watched it fail. The standing record is the paragraph in [`README.md`](README.md#status) that says so of every move in the test count, change by change.

  ⚠️ **There is exactly one exception, and it is named here so that it stays one.** On 2026-08-23 the `DangerousAddRef`/`DangerousRelease` pairs for [adversarial-review findings 6 and 13](docs/reviews/2026-08-18-adversarial-processes.md) went in **with no failing test behind the behaviour**, at the maintainer's decision. The defect is a handle-recycling race: the window is between `ProcessAttributeList.For` returning and `CreateProcessW` reading the number it left in native storage, and between `Dispose` and an in-flight `RegisterWaitForSingleObject`. Neither is deterministically reproducible in this suite, and a test that provoked one by timing would be the very thing the row above forbids. **What was asserted instead is the source-level rule**, which is a weaker claim than a red test and is stated as one: it holds that the pair exists where a raw value escapes, not that the fix is correct. **A second exception is not a precedent — it is a change to this rule**, and that belongs to whoever owns the rule.

## The daily drift check

**Once per day of work, before anything substantive:** read [`drift-check.json`](drift-check.json). If `lastChecked` is today, skip it and say nothing. Otherwise resolve all five upstreams **the way the build resolves them and not the way a registry query defaults** — the table is `_how_to_resolve` in that file, and the trap it exists for is `playwright-core`, which arrives as `@playwright/mcp`'s own exact dependency and never as npm `latest`. Compare against [`upstream-review.json`](upstream-review.json) and write the result back.

**Only stamp `lastChecked` after a lookup actually returned a version** — a date written from intent reads identically to a real one and silences the next check for a day. **Never block work on it:** drift is information, report it, offer [the review procedure](UPSTREAM-REVIEW.md), and carry on with what was asked. **Drift is not a bump** — finding a newer version does not license editing the marker. A confirmed move puts the [re-verification index](kb/re-verification.md) in play, which is the half of a review the golden snapshot cannot do. Why a directive rather than a CI poller: `_why_this_is_enough`, in the same file.

## Scratch work

Agent-produced temporary files go in `.work/` at the repository root — gitignored, created on demand, and nowhere else on the machine. This supersedes any user-global temp-directory convention while working in this repository. Nothing enforces it but `.gitignore`, which keeps the residue out of the tree rather than stopping it being written somewhere worse.
